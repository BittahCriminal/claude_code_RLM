Skill 2.3: Secure APIs published in Azure
This objective deals with securing APIs published in Azure. Organizations often publish APIs in 
Azure and as is the case with any resource you make available publicly, the moment you expose 
the resource, people of nefarious intent will try to exploit that resource. An exploited API can-
not only be used to gain access to other resources in the cloud but may also be attacked in 
such a way as to increase your organization’s Azure bill substantively. In this section, you will 
learn about Azure API Management and the recommended security baseline for API manage-

Azure API Management
Azure API Management is an Azure service that allows you to securely expose Azure and 
specially configured external services as APIs. APIs are standards-based integration tools for 
exposing and accessing data, processes, and applications. APIs allow an organization to create 
an abstraction layer for legacy services, making those services more easily interact with  
modern cloud services and apps. 
Azure API Management includes the following components that run as managed services in 
Azure:
 ■ API Gateway The API gateway is the interface through which client applications inter-
act. The API gateway processes client traffic and forwards it to the appropriate services. 
The API gateway is responsible for verifying API keys and other credentials, enforcing 
usage quotas and rate limits, and transforming requests and responses as specified by 
policy statements. The API Gateway also caches responses to reduce latency and gener-
ates logs, metrics, and traces used for monitoring, reporting, and troubleshooting. The 
self-hosted API gateway allows you to deploy a Linux-based Docker container in your 
on-premises environment connected to the API Management service in Azure. 
 ■ Management plane  The management plane is where you, as the API publisher, provi-
sion and configure API Management service settings, configure API schemas, package 
APIs into consumable products, define policies including quotas and rate limits, view 
analytics information, and manage user access.
 ■ Developer portal  The developer portal is a website that provides documentation 
for the APIs you publish. The developer portal allows you to configure an API to be 
published through an interactive console, allows those that will consume APIs to create 
accounts and subscribe to access API keys, manage API keys, view analytics related to 
their own usage, and download API definitions.
API Management has the following built-in groups:
 ■ Administrators  Can manage API Management service instances and create APIs and 
the operations and products that developers access. Subscription Global Administrators 
are members of this group.
 ■ Developers These are developers you grant access to the developer portal. They build 
applications that call the functionality of the APIs that you publish. Developers can sign up

Configure storage account access keys

reason to believe that a storage account key has leaked, the best practice is to rotate them

Skill 4.6: Configure delegated access
Shared Access Signatures (SAS) allow you to provide secure, granular, and delegated access to 
storage accounts. Using an SAS, you can control what resources a client can access, the client’s 
permissions to those resources, and the length of time that access will persist. Stored access 
policies allow you to specifically control service-level shared access signatures. You can config -

Shared Access Signatures
An SAS is a signed Uniform Resource Identifier (URI) that provides the address of one or more 
storage resources and includes a token that determines how the client may access the resource.

Azure Storage supports the following types of SAS:
 ■ User delegation SAS  User delegation SAS can only be used with Blob Storage. Entra 
ID secures user delegation SAS and the permissions configured for the SAS. 
 ■ Service SAS  Service SAS is secured with storage account keys. This SAS delegates 
access to one type of storage resource. Service SAS can be configured for Azure Files, 
Blob Storage, Queue Storage, or Table Storage.
 ■ Account SAS Account SAS is secured with the storage account keys. These keys can 
be used to delegate access. In addition to all the operations that can be made available 
with user delegation SAS or service SAS, account SAS allows you to delegate access to 
operations that apply at the service level, such as getting and setting service properties. 
Account SAS also allows you to delegate access to read, write, and delete operations on 
blob containers, file shares, tables, and queues that are not possible with a service SAS.
SAS comes in the following two forms:
 ■ Ad hoc SAS An ad hoc SAS includes the start time, expiry time, and resource  
permissions within the SAS URI. All SAS types can be ad hoc SAS.
 ■ Service SAS with stored access policy  Stored access policies are configured on 
resource containers, which include blob containers, tables, queues, or file shares. A ser -
vice SAS with stored access policies inheritss the start time, expiry time, and permissions 
configured for the stored access policy.
As is the case with storage account access keys, if an SAS is leaked, anyone who has access 
to the SAS has access to the storage resources to which the SAS mediates access. Application 
developers should also remember that SASes periodically expire, and if the application is not 
configured to automatically obtain a new SAS, the application will lose access to the storage 
resources to which the SAS mediates. 
Microsoft’s best practices for using SAS include the following:
 ■ Use user delegation SAS when possible  This type of SAS has the best security 
because it is secured through a user’s Entra ID credentials, meaning account keys will 
not be stored with the application code.
 ■ Be ready to revoke an SAS when necessary  If you determine that an SAS has been 
compromised, ensure that you can quickly revoke the SAS and replace it with one that is 
not compromised. 
 ■ Configure stored access policies for service SAS  An advantage of stored access 
policies is that you can revoke permissions for a service SAS without regenerating stor-
age account access keys. 
 ■ Configure short expiration times for ad-hoc SAS  If an ad hoc SAS is compromised, 
the short expiration time will ensure that the compromised SAS isn’t valid for a long 
time.
 ■ If necessary, ensure clients renew SAS  If clients regularly make requests to storage 
using SAS, configure the application so that the client can request SAS renewal before 
the SAS expires.

Implement Azure SQL Database Always Encrypted
Always Encrypted allows you to protect specific types of sensitive data with a known, recogniz -
able pattern, such as a passport, tax file identification, and credit card numbers. When Always 
Encrypted is enabled, clients interacting with the database server will encrypt the sensitive data 
inside the client applications and will not forward the encryption keys used to decrypt that 
data to the database server that will store that data. This ensures that administrators who man-
age Azure SQL servers cannot view sensitive data protected by Always Encrypted. 
SQL Always Encrypted differs from TDE in scope, visibility, and key management. TDE 
encrypts entire databases at rest, and is transparent to users, using database-managed keys. 
SQL Always Encrypted targets specific columns, keeping data encrypted in memory and during 
processing, with keys managed externally
Deterministic or randomized encryption
Always Encrypted supports two forms of encryption: deterministic and randomized:
 ■ Deterministic encryption  When you use deterministic encryption, the same 
encrypted value will always be generated for the same plain text value, though each 
database will be unique. Implementing deterministic encryption will allow you to 
perform point lookups, equality joins, grouping, and indexing on encrypted columns. 
It may, however, allow unauthorized users to guess information about encrypted values 
by looking for patterns in encrypted columns. This is especially true if there is a small  
set of possible values. Deterministic encryption requires that the column collation is 
configured with a binary2 sort order for character columns.

Skill 5.6: Azure SQL Firewall
Securing Azure SQL isn’t simply a matter of restricting access on the identity plane and ensur-
ing that data is classified, encrypted, and masked. One of the oldest methods of securing 
data, restricting access based on network traffic properties, also plays a part. Firewalls are 
fairly straightforward when deploying SQL on a virtual machine or bare metal server. Even 
though Azure SQL follows the same basic principles, there are several differences to consider 
when understanding firewall rules when a SQL instance runs as a Platform as a Service (PaaS) 
offering. 
Understanding Azure SQL firewalls
Azure SQL firewall rules allow you to block or allow traffic using the IP address of the client 
attempting to interact with the Azure SQL instance or database. Azure SQL uses firewalls at two 
different levels, the Azure SQL instance level and the Azure SQL database-level. Network traffic 
is processed by firewall rules at the database-level before being processed by the firewall rules 
at the server-level.
You should configure firewall rules at the database level as a priority because this allows you

Database-level firewall rules
Database-level firewall rules are configured at the individual database-level and are processed 
before server-level firewall rules. You can only configure database-level firewall rules using 
Transact-SQL statements. You do not have to configure database-level firewall rules and can 
allow and deny access only at the server-level. You configure database-level firewall rules when 
you want to isolate users of one database from another. For example, you want to allow users 
from one set of IP addresses access to one database and users from another set of IP addresses 
access to another database. Remember that you can also isolate users based on identities 
stored in Entra and SQL logins. Before creating database-level firewall rules, you need to 
configure at least one server-level firewall rule. Database-level firewall rules have the following 
properties:
 ■ Each user database can have up to 256 database-level IP firewall rules.
 ■ Database-level firewall rules are processed before server-level firewall rules. 
 ■ If you configure an IP address range in a database-level IP firewall rule that is not within 
the range of the allowed ranges at the server-levels, only clients with IP addresses con-
figured in database-level rules will be able to access the database.

Deploy secure infrastructures by using a landing zone
An Azure Landing Zone is an environment to host Azure workloads pre-provisioned through 
code. It uses a set of defined cloud services and best practices to add foundational capability  
while providing cloud adoption teams with a well-managed environment to run their 
workloads. 
Everything starts with a subscription that can be considered a unit of management not only 
for new application development but also to accelerate the migration of existing applications. 
It is important to align the subscription with your business needs. Even if you have multiple 
subscriptions, landing zones should be provided to support existing and new workloads. 
When necessary, you may also aggregate multiple subscriptions into a single management 
group (MG), allowing you to easily scale while keeping centralized management for multiple 
subscriptions.
Azure Landing Zone’s conceptual architecture design presumes that a specific MG and sub -
scription hierarchy are available for all operations management subscriptions, which may not 
be aligned with your operating model. As your organization grows and continues to evolve, 
your operational model may change, leading to another resource migration into separate sub-
scriptions and technical migration challenges. There are two types of Azure landing zones:
 ■ Platform landing zone  A subscription that securely shares services such as identity, 
connectivity, and management to applications within application landing zones. Typi-
cally, centralizing these services enhances operational efficiency.
 ■ Application landing zone  A subscription designated for hosting an application. 
These landing zones are pre-provisioned via code, and policy controls are assigned to 
them through management groups.

Creating a Key Vault certificate is an asynchronous process. When this operation is requested, 
a Key Vault certificate request is generated, and an HTTP status code of 202 (Accepted) is 
returned. The progress of the request can be monitored by continuously checking the status of 
the pending object created during this operation. The complete URI of the pending object is 
provided in the LOCATION header. Once the request to create a Key Vault certificate is finalized, 
the status of the pending object transitions from in progress to completed, and a new version of 
the Key Vault certificate is generated, becoming the current version.
When a Key Vault certificate is initially created, a corresponding addressable key and secret 
are also generated with matching names. If the the name is already in use, the operation will 
fail with an HTTP status code of 409 (conflict). Attributes for the addressable key and secret are 
derived from those of the Key Vault certificate. These entities are marked as managed keys and 
secrets, with their lifespan governed by Key Vault, and are thus read-only. It’s important to note 
that if a Key Vault certificate expires or is disabled, the associated key and secret become unus -
able. For the first operation to create a Key Vault certificate, a policy is mandatory. 
Subsequent create operations can include a policy to replace the existing one. In cases 
where no policy is provided, the service’s policy resource is used to create the next version of 
the Key Vault certificate. During the creation of a subsequent version, the current Key Vault 
certificate and its corresponding key and secret remain unaltered.

Secret
When discussing secrets in the context of Key Vault, you can simply think of a secret as a pass-
word you want to keep safe or a database connection string you want to keep secure. Having 
said that, if you are a developer and are building an app that uses Key Vault APIs to access a 
secret, you will see the secret as a string during 
accept and return operations. 
Key Vault secrets are internally stored and managed as sequences of octets (8-bit bytes), 
with a maximum size of 25 kilobytes each. The Key Vault service does not offer semantics for 
secrets; rather, it accepts the data, encrypts it, stores it, and issues a secret identifier (ID). This 
identifier can be utilized to retrieve the secret at a later point in time. It is important to mention 
that depending on the sensitivity of the data and the scenario’s requirement that you have to 
comply with, you should consider adding an extra layer of protection for the data by encrypt-
ing the data using a separate protection key prior to storage in Key Vault.
For scenarios where you want a more custom approach to interpret the type of secret, 
you can leverage the contentType field. You can designate the content type of a secret, which 
helps interpret the secret data upon retrieval. The maximum length allowed for this field is 
255 characters. Use this capability always when  you need to provide guidance on interpreting 
the secret data. One common scenario where this approach applies is when you need to store 
both passwords and certificates as secrets. In this case, you can utilize this field to distinguish 
between them.

Key Vault offers automated cryptographic key rotation, enabling users to set up Key Vault to

encryption keys at least once every two years to adhere to cryptographic best practices.
Key rotation involves creating a new version of an existing key with updated key material. 
Target services should utilize a versionless key URI to seamlessly access the latest key version. 
Your data encryption solution needs to store versioned key URIs alongside the data, ensuring 
that decryption/unwrapping operations point to the same key material used for encryption/
wrapping processes to prevent service disruptions. Currently, all Azure services adhere to this 
pattern for data encryption.

Configure backup and recovery of certificates, secrets,  
and keys 
Azure Key Vault offers automated features to ensure availability and prevent data loss. Only 
back up secrets if you have a compelling business reason. Doing so may present operational 
complexities, such as managing multiple logs, permissions, and backups as secrets expire or 
rotate. Key Vault guarantees availability during disaster scenarios and will autonomously  
redirect requests to a paired region without user intervention. 
For safeguarding against accidental or malicious deletion of secrets, configure soft-delete and 
purge protection features on your Key Vault. When this chapter was written, Key Vault did not 
support backing up an entire vault in a single operation. A problem that you may face trying to 
back up secrets is that the backup operation creates a point-in-time snapshot. However, secrets 
might renew during a backup operation, which may cause a mismatch of encryption keys. 
Another important point to consider when planning your backup strategy for Key Vault 
is that the Key Vault object that was backed up, such as a secret, key, or certificate, will be 
retrieved as an encrypted blob. This encrypted blob cannot be decrypted outside of Azure. To 
access usable data from this blob, you must restore it into a Key Vault located within the same 
Azure subscription and geographical region.
