Identify and monitor external assets by using Microsoft 
Defender External Attack Surface Management
Microsoft Defender External Attack Surface Management (Defender EASM) persistently 
detects and charts your digital attack surface, offering an external perspective of your online 
infrastructure. The intent is to look at your organization from the outside-in like an attacker 
would. The process happens in three major phases:
 ■ To perform the initial discovery, sensors and crawlers scan the Internet and your  
external, Internet-facing profile.
 ■ This initial scan will enable you to understand the unknown assets, shadow IT, and 
legacy services you still have operating online.
 ■ After gathering and rationalizing this information, Defender EASM builds an accurate 
and up-to-date catalog of your organization’s resources and assets.
This insight empowers security and IT teams to uncover unknowns, assess risks, neutralize 
threats, and broaden vulnerability and exposure management beyond the firewall. Leveraging 
vulnerability and infrastructure data, Attack Surface Insights highlights critical areas of concern 
for your organization. Microsoft employs proprietary discovery technology that recursively 
scans infrastructure, identifying connections to established legitimate assets to deduce 
their relationship with the organization and reveal previously undisclosed and unmonitored 
properties. 
These legitimate assets, termed discovery’ seeds,’ serve as the initial focus for Defender 
EASM, which traces robust connections to these entities, recursively exploring further connec-
tions to compile your comprehensive Attack Surface. The list of assets that are discoverable by 
Defender EASM includes:
 ■ Domains
 ■ Hostnames
 ■ Web pages
 ■ IP blocks
 ■ IP addresses
 ■ ASNs
 ■ SSL certificates
 ■ WHOIS contacts

Defender for Cloud uses advanced security analytics and machine-learning technologies to 
evaluate events across the entire cloud fabric. The security analytics include data from mul-

(DCU), the Microsoft Security Response Center (MSRC), and external feeds. This is the core of 
Defender for Cloud threat detection, and on top of that, there will be different mechanisms of 
detection according to the workload.
Different workloads will have different threat landscapes, meaning that threat protection

Defender for Storage
Visibility and control are becoming critical with regard to the security hygiene of workloads. 
Exposed storage containers are a typical scenario targeted by threat actors that are utilizing 
custom scanners built specifically to identify public containers. Microsoft Defender for Storage 
is an Azure-native layer of security intelligence that detects unusual and potentially harmful 
attempts to access or exploit your storage accounts.
Defender for Storage can be enabled for data stored in Azure Blob Storage (Standard/ 
Premium StorageV2, Block Blobs), Azure Files, and Azure Data Lake Storage (ADLS) Gen2. You 
can enable Defender for Storage on the subscription level just like any other plan, but you can 
also enable it only on the storage accounts you want to protect. 
Defender for Storage also has malware scanning capabilities available. Malware Scanning in 
Defender for Storage safeguards your Azure Blob Storage from malicious content by conduct-
ing comprehensive malware scans on uploaded files in near real-time, leveraging Microsoft 
Defender Antivirus capabilities. This feature helps meet security and compliance requirements 
for managing untrusted content. As an agentless software as a service (SaaS) solution, it offers 
easy setup at scale, requires no maintenance, and supports automated response at scale.
Defender for Storage continually analyzes the telemetry stream generated by the Azure 
Blob Storage and Azure Files services. If a potential malicious activity is detected, a security 
alert is generated. Defender for Storage provides alerts based on different types of threats, as 
shown in the list below:
 ■ Unusual access to an account  Threats such as access from a TOR exit node.
 ■ Unusual behavior in an account  Behavior that deviates from a learned baseline, 
such as an unusual deletion of blobs or files. 
 ■ Hash reputation-based malware detection  As files are uploaded to the storage 
account, they are analyzed by the hash reputation system, which looks into Microsoft 
Threat Intelligence to determine if the file is suspicious. It is very important to under -
stand that this is not an antimalware feature since it only looks into the file hash and 
does not scan the file.
 ■ Unusual file uploads  The upload deviates from the normal pattern, such as the 
upload of cloud service packages and executable files.
 ■ Public visibility  Related to attempts to break in by using public scanners.
 ■ Phishing campaigns  Related to scenarios where a piece of content hosted on an 
Azure Storage account was identified as part of a phishing attack impacting Microsoft 
365 users.

The cyber kill chain is a threat model described in 2011 by analysts from Lockheed Martin.  
The model was designed to help security teams and researchers organize their thinking about 
detecting and responding to threats. The model is now generally accepted and is part of the 
general lexicon of all security professionals.
The original cyber kill chain was divided into these phases:
1.
 Reconnaissance  During this phase, the attacker identifies the best targets.
2. Weaponization  Here, files are altered to make them weapons against a target system 
and are used to install malicious code.
IMPORTANT W hen you enable Defender for Servers on your subscription, its coverage does 
not automatically extend to your Log Analytics workspaces. You must enable Defender for 
Servers for each workspace individually. Note that Defender for Servers on workspaces  
supports only Plan 2. 
Humble Bundle Pearson Microsoft Press Exam Ref – © Pearson. Do Not Distribute.

CHAPTER 7  Microsoft Defender for Cloud330
3. Delivery At this point, weaponized files are placed on the target.
4. Exploitation  During this phase, weaponized files are detonated—that is, they’re run 
on the victim system.
5. Installation  At this point, a back door is installed on the compromised system, giving 
the attacker persistent access.
6. Command-and-control (C&C)  Here, malware on the compromised system  
communicates with a C&C system that gives the attacker access to the resources 
required to carry out their objective.
7. Actions on objectives  At this point, the attacker carries out their objectives, which 
might be predefined or might have evolved based on discovery. The cyber kill chain 
was defined when on-premises computing was the norm. Now that cloud computing is 
considered a better option, the cyber kill chain must be re-evaluated and updated.  
A reconfiguration of the cyber kill chain might include the following phases:
 ■ Active recon In this phase, the attacker uses numerous footprinting methods to 
identify the operating system or services being used, which will be the focus of the 
attack.
 ■ Delivery Because most public cloud assets lack a logged-on user, attackers will 
need to hack the system—typically by finding unpatched exploits that can be  
leveraged against the system or service.
 ■ Exploitation  This phase focuses on problems on the server side instead of the  
client side.
 ■ Persistence  Unlike client-side systems, which are rebooted often, server- and  
service-specific systems are rarely rebooted. The exploit code must remain in 
memory to remain persistent within the system. That is the focus of this stage.
 ■ Internal recon  Attacks against cloud-based systems are server-based. Therefore, 
rather than installing new tools, the attacker can simply use the server’s built-in tools 
to conduct the attack. This helps the attacker remain undiscovered, as installing new 
tools could trigger an alert.
Defender for Cloud has a type of alert called a security incident , which is raised in the 
dashboard whenever the system identifies multiple alerts that, when correlated with each 
other, indicate that those alerts belong to the same attack. A security incident uses the fusion 
capability to correlate the alerts that appear to be related. Each phase of the cyber kill chain 
individually indicates that something bad may be happening but cannot offer you complete 
certainty of the scenario. However, when you correlate these findings, you can have a better 
idea about the attack. A security incident appears in the alert dashboard in the format shown

Workflow automation is a capability that helps you to automatically react on either a new alert, 
or on a new recommendation. It leverages Azure Logic Apps as the automation artifact, and 
within the Logic App, you are offered almost unlimited possibilities to automate processes. To 
enable automation, the workflow automation feature brings additional Trigger Types to Logic 
Apps:
 ■ The Recommendation  trigger will start a Logic App playbook in the following 
conditions:
 ■ A resource has been added to a recommendation as a result of an assessment.
 ■ A resource status has changed within a recommendation as a result of an assessment, 
while the resource status can be healthy, unhealthy, or not applicable.
 ■ A Logic App is manually triggered from a recommendation within Defender for 
Cloud. 
 ■ The Security Alert  trigger will start a Logic App playbook in the following conditions:
 ■ A new security alert is created in Microsoft Defender for Cloud.
 ■ From an alert, the Logic App is manually triggered.
 ■ The Regulatory Compliance Standards trigger is triggered when a compliance  
control’s status within a standard is changed. In this case, the status can be failed, 
passed, skipped, or unsupported.

you could let the Logic App create a JIRA or ServiceNow ticket or notify stakeholders about

Evaluate alerts and incidents in Microsoft Sentinel
In today’s cyber landscape, the number of threats is increasing, which leads to an increasing 
number of alerts security teams need to respond to. Microsoft Sentinel can enrich alerts with 
data from other sources, investigate entities for more context, orchestrate across the organi-
zation, and act on incidents. Microsoft Sentinel can reduce the time to resolution for security 
incidents and allow security teams to focus on the most important alerts. Many, if not most, 
of these alerts conform to recurring patterns that can be addressed by specific and defined 
courses of action, which can be automated to allow the security operation center to focus on 
what matters most.
An incident in Microsoft Sentinel can be created through 
 ■ A scheduled analytics rule based on either one or more alerts or notable events
 ■ An incident created by one of the data connectors based on one or more alerts
 ■ A Fusion incident based on fused and correlated events
 ■ An incident based on a match with one or more threat indicators
 ■ An incident based on a hunting query
 ■ A manually created incident through the Security.Insights API, PowerShell, or the 
Azure portal

In Microsoft Sentinel, the rules can be categorized according to their detections:
 ■ Anomaly These are built-in rules that use machine learning (ML) against your data to 
detect specific types of threats. These rules have a few parameters and thresholds that 
can be configured, but Microsoft protects the ML models used. You can enable these 
rules in testing mode first to see how they would perform against your data, and when 
ready, you can move them to production.
 ■ Fusion This rule has no settings that can be configured. It can only be enabled or 
disabled in the workspace. If the alerts are part of the same attack, the fusion rule will 
correlate low-fidelity alerts across alert rules into a single high-fidelity incident.
 ■ Machine Learning behavioral  These rule templates are based on Microsoft  
proprietary ML algorithms. The ML is applied to specific data sources and events to 
detect anomalous behavior in the data.
 ■ Microsoft Security  Enables you to create an incident in Microsoft Sentinel from any 
existing security alert that comes from these solutions.
 ■ Near-real-time (NRT)  Allows you to run detections up to the minute. Because 
scheduled rules only allow a query to run as little as once every 5 minutes, NRT rules are 
hardcoded to run every 1 minute on the last minute of data.
 ■ Scheduled  A typical SIEM rule that runs on a timed basis and looks at data from a 
specific period of time. These rules trigger on a configured threshold.
 ■ Threat Intelligence (TI)  These rules match TI data from Threat Intelligence against 
Common Event Format (CEF), DNS, and Syslog data.
