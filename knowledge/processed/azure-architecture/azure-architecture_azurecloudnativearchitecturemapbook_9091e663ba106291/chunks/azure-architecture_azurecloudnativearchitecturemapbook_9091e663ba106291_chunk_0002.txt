One area where
developers
often struggle is
OpenID Connect
(
OIDC
) and
OAuth
—both
of which are foundational in cloud-native applications. A solid grasp of the different token types and authorization flows is essential, since lacking this knowledge can significantly hinder your effectiveness as an Azure developer. In Azure, the
main
Identity Providers
(
IdPs
) are Entra ID and Entra External ID—typically used for B2B and B2C scenarios, respectively. However, many solutions also make use of third-party providers such as Duende or Keycloak. Regardless of the provider, all of them are built upon the same standards: OIDC and OAuth. Here are the essential notions you must remember about these standards:
Access tokens
are used to authorize access to protected resources, whether they’re Azure services or your own APIs. They are commonly used by
Single-Page Applications
(
SPAs
) to
call APIs directly or are managed by
a
Backend-for-Frontend
(
BFF
) that acts as the SPA’s gateway. Access tokens are also frequently used in service-to-service communication scenarios. When acting as a
client
, your application must request an access token to consume a protected resource. When acting as a
resource
(for example, an API), it must validate the token presented by the caller to ensure the request is authorized.
Refresh tokens
are long-lived tokens used to obtain new access tokens on behalf of a user when previously acquired access tokens have expired.
ID tokens
are the result of user authentication and often contain profile information, although it is not strictly required by the standard. ID tokens are intended for the client application only, enabling it to verify the user’s identity and establish a session. They should never be sent to APIs, as they are not designed to authorize API access—that is the role of an access token.
All these tokens can be acquired
through various authorization flows, such as
Proof Key for Code Exchange
(
PKCE
),
Authorization Code Grant
, and
Client Credentials Grant
, which
are
the most commonly used flows. The
On-Behalf-Of
(
OBO
) flow is more advanced and
typically used to retrieve access tokens to access other backend APIs on behalf of the user. Gaining a solid understanding of both token types and authorization flows will greatly enhance your developer experience in Azure and the cloud in general.
A best practice in
Azure is to use
either
managed identities
or
workload/federated identities
to
access resources securely. Both techniques require the infrastructure and the permissions to be pre-configured according to the application’s needs. Regardless of the identity type, the client credentials grant flow is always used to obtain access tokens in these scenarios.
Managed identities are typically used in two different ways. The first option consists of having the code directly, using the identity to access the resource, as shown in
Figure 6.4
.
Figure 6.4 – Code accessing a resource using managed identities
The first step is
to request an access token for the target resource. When using the Azure SDK (typically
Azure.Identity
), the request is made transparently by the SDK to a local endpoint, not directly to Entra ID. This
local endpoint, provided by Microsoft, acts as a proxy that performs the actual token request to Entra ID and returns the token to the application. Note that this proxy layer caches tokens for up to 24 hours.
Once the token is obtained, the application can use it to access the resource. The managed identity used in this process can be either system-assigned or user-assigned. System-assigned identities
are tied to the life cycle of the resource, such as a web app, and are automatically created and deleted with it. User-assigned identities
are standalone Azure resources that can be associated with one or more services. The main benefit of using managed identities is that the identity credentials are entirely managed by Azure itself.
For accessing Azure Key Vault, which is commonly used to store sensitive information, we can either follow the approach illustrated in
Figure 6.4
, where the code explicitly retrieves secrets through the proxy, or rely on Azure to fetch the secret on our behalf—making the code agnostic of where the secret is stored—as shown in
Figure 6.5
.
Figure 6.5 – Using Key Vault references to fetch secrets
Although this
might look similar to
Figure 6.4
, it is not at all the case. Dotted circles (steps 1 and 2) are actions performed by Azure, not by our code. In this case, our code accesses sensitive information like any regular configuration setting. Azure itself pulls the secret from Key Vault when the web app starts, thanks
to a
Key Vault reference
that we define in the settings. Such a reference looks like this:
@Microsoft.KeyVault(SecretUri=https://myvault.vault.azure.net/secrets/mysecret)
. Key Vault references
can be used from various services, including App Service, function apps, API Management, and Azure App Configuration. With this approach, your code doesn’t need to handle managed identity authentication or connect directly to Key Vault—Azure resolves the secret for you. However, a limitation of this method is that Azure doesn’t automatically refresh the reference when a secret is rotated, since it fetches Key Vault every 24 hours or, at best, every 4 hours. In contrast, when accessing Key Vault programmatically, you have more control—for example, caching the secret value and implementing a retry mechanism if an expired secret causes a failure. You might choose a specific method based on how often the secret is rotated.
When managed identities are not available—such as when the application runs in AKS—we must use workload identities instead. While the core principle remains the same (avoiding the need to store credentials in application configuration), the implementation differs significantly. With workload identities, Azure uses federated identity credentials linked to a Kubernetes ServiceAccount, which in turn is linked to a Pod. The Azure identity is bound to the ServiceAccount
via a trust relationship, allowing the application to authenticate securely to Azure without storing secrets. This approach relies on OIDC federation between the AKS cluster and Entra ID. Your application then requests an access token to Entra ID in exchange for the projected Kubernetes token. There is no more proxy involved. Note that AKS used to support Pod-managed identities in the past, but this has been deprecated, making workload identities the only option.
All of this, whether using managed or workload identities, requires apps to be registered in Entra ID. You can rely on the
Azure.Identity
SDK for both managed and workload identities.

Zooming in on some cloud-native application design patterns and architecture styles

Figure 6.7 – Common patterns and architecture styles
While there are no hard rules
for designing applications specifically
for on-premises or cloud environments, on-premises systems are often monolithic, whereas cloud applications tend to be more distributed. This book will not delve into the debate over which approach is superior, as that is beyond its scope. Instead, it’s important to note that the cloud can support any architectural style—including monoliths. One step toward breaking monoliths is by adopting the so-called
modular monoliths
, which is a way to introduce logical
modularity at the level of the code itself while still deploying the application as a whole. Modular monoliths improve the readability and maintainability of the application code, but do not allow for independent deployment, scaling, or component-specific resilience mechanisms, unlike distributed architectures and microservices.
Distributed monoliths
, on
the other hand, are the other extreme, as they give a false impression of autonomy and independence but are still tightly coupled. An example of a distributed
monolith could be the split of a single service into three different services that call each other synchronously at runtime and that are all reading and writing to the same database. Some call this microservices, but let’s face it, these are just different pieces of the same puzzle that are still highly dependent on each other. Since the main subject of this book is not about software architecture, let’s simply look at common patterns that help decouple application components and bring higher resilience.
Most modern applications are API-centric, and Azure API Management supports patterns such as Gateway Offloading, Gateway Aggregation, Gateway Routing, and Circuit Breaker. All of these patterns are either built into the service or made possible through the use of policies. There is, however, one rule of thumb to respect: keep it simple and do not write business logic in policies. APIM policies are very powerful but not so easy to test. For example, there is no code coverage (unit testing); integration tests can be put in place in CI/CD pipelines
using
Postman Collections
, but this requires extra efforts and skills. Interestingly, APIM policies can be debugged using Visual Studio Code. However, simple aggregation using custom logic or GraphQL, as well as dynamic backend routing, can be easily put in place while not compromising maintainability and testability. The tool available at this GitHub repo may help you create and test policies:
https://github.com/Azure/azure-api-management-policy-toolkit
. With the rise of Generative AI, Microsoft is positioning Azure API Management as an AI gateway, for which many of the preceding patterns are used.
Figure 6.8
shows a routing example across two different instances of Azure OpenAI, making the client totally agnostic of the underlying AI architecture.
Figure 6.8 – Gateway routing across multiple Azure OpenAI instances
In
Figure 6.8
, Azure API Management
is configured with a backend pool consisting of two Azure OpenAI instances. A simple policy is applied to handle HTTP status codes 429 (Too Many Requests) and 503 (Service Unavailable), enabling seamless request failover between backends—completely transparent to the client. This pattern also allows Azure API Management to take over the authentication process: using its managed identity, it acquires access tokens and authenticates with the OpenAI instances. As a result, clients do not interact directly with the AI backends, enhancing both security and abstraction. As an application architect, you must consider such patterns whenever possible and offload such duties to Azure services instead of reinventing the wheel in code. The AI gateway pattern principles also apply to your own backend services. You can find a lot of samples in the GitHub repo:
https://github.com/Azure-Samples/AI-Gateway
. Azure API Management goes far beyond these basic patterns and also helps standardize, monitor, secure, and design APIs regardless of the application use case.
Distributed
applications often involve message and event brokers such as Azure Service Bus and Event Grid and their related point-to-point, pub/sub, load-leveling patterns, which we already explained in
Chapter 2
. Another common messaging pattern is the Claim Check pattern, which handles large messages by simply storing the large payload in an external system such as Blob Storage and embedding a reference to it in the message sent to the message broker, such as Azure Service Bus.
The message handler can go grab the actual large payload from Azure Blob Storage instead of saturating Service Bus or storage account queues with large messages. The Claim Check pattern is very commonly used, so make sure to master it. A few years ago, it was mandatory to use Claim Check because Azure Service Bus message sizes were rather limited. Nowadays, we can store large messages directly into Service Bus, but it is nevertheless a questionable approach to do so.
When working with data stores, it’s useful to distinguish between code-level design patterns—such
as
Command Query Separation
(
CQS
) and Event Sourcing—and native data store features such as
Change Data Capture
(
CDC
) or
Cosmos DB’s Change Feed.
Command Query Responsibility Segregation
(
CQRS
) bridges
both domains, for instance, by routing write operations to a primary Azure SQL database while directing read-only queries to its replicas that can be made automatically available by Azure SQL. As an application architect, it is essential to evaluate and leverage built-in data capabilities that support or enhance design patterns. For example, Change Feed in Cosmos DB can
support E
vent Sourcing
scenarios and facilitate the creation
of
materialized views
or
cache invalidation
when
used with services such as Azure Functions. Let’s now go through a practical example with our use case.
Use case – serverless invoice processing pipeline
Scenario and first analysis
:
Contoso is a financial services firm that receives hundreds of customer invoices daily from partners. These files are uploaded in JSON format and must be validated, parsed, and then routed to different back-office systems based on their contents (for example, domestic versus international payments, amounts subject to further approval, and so on). They are looking for a scalable solution that can handle peak loads while remaining cost-friendly.
Let’s first
extract the keywords in this scenario that demand our focus:
Hundreds of customer invoices daily
: Note: hundreds, not thousands or millions. Given that invoices are also typically rather small documents, we know that the overall throughput will remain quite limited.
Peak loads
: We know that the load will not be linear. If we have hundreds of invoices per day, this might be 200 in the morning and 200 at the end of the day, or there might be busier days than others. In any case, the volume remains relatively low but we should still be able to scale when needed.
Financial services
: Contoso is in the financial sector, so we can imagine that the solution should adhere to high security standards, although none is explicitly expressed in the scenario.
Validated, parsed
: We must be prepared for a parsing process.

The Azure Functions

In our scenario, we’re using the runtime in a straightforward manner—to trigger code execution when a blob is added to a storage container and to enqueue a message to a Service Bus topic. At first glance, this should be simple, thanks to the built-in Blob Storage trigger and Service Bus output binding. However, as is often the case, the devil is in the details. Our design requires promoting custom metadata properties so that subscribers can filter messages and receive only the invoices relevant to them. Unfortunately, the Service Bus output binding doesn’t currently support promoting such properties. To meet this requirement, we must instead use the native Service Bus SDK directly.
Secondly, while we haven’t yet applied strict network hardening to our solution, we aim to follow best practices for authentication by leveraging managed identities to access both our business storage account and Service Bus. This approach, though more secure, can be challenging to implement—especially since most online examples rely on basic connection strings rather than identity-based access.

Zooming in on data platform capabilities
Patterns such as Kappa, Lambda, Medallion, and Lakehouse, to name a few, are built upon a common set
of underlying capabilities. By aligning these capabilities with Azure services, we aim to simplify the process of selecting the right service for your specific architectural objectives. A few data services, such as Azure Databricks and Synapse Analytics, are versatile and allow you to tackle most data scenarios. Databricks is slightly more comprehensive, but both offerings are very complete. Organizations that have a Databricks ecosystem on-premises typically favor Azure Databricks, while Microsoft shops typically favor Synapse. Databricks originally emerged with a focus on data science, whereas Synapse was designed to address data warehousing and traditional business intelligence needs. In the meantime, Synapse grew significantly to also cover modern data science aspects.

There are a few sub-categories, such as data ingestion, data processing, serving layers, storage, and so on. Let’s start with the data ingestion category.
Data ingestion
IoT Hub
and
Event Hubs
are both
highly scalable ingestion layers. As its name indicates, IoT Hub
is the Azure service for any IoT scenario. The service is able to
establish bi-directional communications with IoT devices and can be supplemented with IoT Edge and IoT Edge modules to accommodate enterprise-grade scenarios
matching industry standards, where industrial networks typically do not directly connect to the internet. Event Hubs is a general-purpose ingestion service for high-throughput data streaming. Event Hubs is commonly used for application telemetry and real-time data collection. For example, Azure API Management has a built-in

Business Activity Monitoring

BAM

Events landing in both IoT Hub and Event Hubs can be persisted in other data services, such as Azure Data Explorer, Cosmos DB, or ADLS Gen2, among others, using Stream Analytics or other processing services to process and transfer the data to downstream stores. It is worth noting that Azure Data Explorer can also directly use Event Hubs as an input.
Data processing
Data processing
can take various forms—batch processing, stream processing, or event-driven
processing of discrete data

(
MPP

In contrast, Fabric Dataflow Gen2 enables users to build ingestion and transformation pipelines using Power Query, without writing any code. This service is designed for power users and citizen developers who prefer a low-code experience. When it comes to batch processing, both Azure Databricks and Synapse Analytics with Spark runtime are very good options. One of the key decision factors about choosing Databricks or Synapse for batch processing is whether you need to look up reference data from external relational stores. At this stage, only Databricks provides this capability. Databricks is also the only one to propose

/

Finally, for stream

Zooming in on HTAP
Traditionally,
online transaction processing
(
OLTP
) systems, such
as relational databases, and
online analytical processing
(
OLAP
) systems, such as

performance needs and data models. HTAP eliminates the need to separate these workloads, enabling real-time analytics directly on live data. HTAP is transformative because it eliminates the need to copy data, which is time-consuming to maintain, prone to staleness, and can introduce inconsistencies.
Additionally, in traditional architectures, application teams typically only consider their operational system as the system of record, while data teams rely on the raw layer available in their data lake. With HTAP, all teams can align on a single, shared data store as the authoritative source.
However, this advanced capability—long sought after by data architects—has yet to become mainstream. As you can see in

Operational database systems
Azure offers a variety of OLTP systems, including relational databases such as Azure SQL and PostgreSQL. However, the flagship OLTP service is undoubtedly Cosmos DB. As of 2025, it remains the
only Azure service that supports multi-master writes across multiple regions at a global scale, while also delivering sub-2-millisecond latency for both reads and writes. Cosmos DB is packed with features that make it a uniquely powerful offering.
That said, as is often
the case with feature-rich platforms, teams sometimes adopt Cosmos DB too quickly without fully understanding its design principles. This can lead to suboptimal performance, escalating costs, and ultimately, a need to revisit the design. Let’s take a closer look at this powerful yet complex service to better understand how to use it effectively through a mini use case scenario.
Let’s imagine that you are developing a mobile app to manage wine cellars. The app is made available through the different app stores, and you expect potentially many users, so you have to make it scalable and accessible worldwide. A high-level solution could be something like we explained in
Chapter 3
,
Infrastructure Design
, in our
Global API platform use case
, where you proxy your backend services with a multi-region API Management instance, and have backend services in corresponding regions, each talking to their own regional Cosmos DB.
Figure 7.9
shows a simplified version of it to refresh your memory.
Figure 7.9 – Simplified multi-region solution
As a global service, Azure Front Door is inherently multi-region aware. Our API layer builds on this by leveraging Azure API Management’s native multi-region capabilities. On the backend, services are
deployed across multiple regions, and Cosmos DB is configured with multi-master writes in all enabled regions. Together, these
elements ensure that our architecture consistently delivers the fastest and most responsive user experience—regardless of the user’s location worldwide.
However, global distribution alone is not enough—performance also depends heavily on how your Cosmos DB is designed. Without following a few key design principles, even the most elegant and appealing mobile app can quickly become sluggish and less engaging for end users. Here are a few essential guidelines to consider when using Cosmos DB:
Avoid hot partitions
: Cosmos DB scales horizontally by distributing data across multiple logical partitions, which are then mapped to physical partitions. If data is not evenly distributed—often due to a poorly chosen partition key—some partitions may receive a disproportionate volume of requests or data. This results in hot partitions, which can degrade performance and eventually lead to throttling or full partitions.
Avoid cross-partition queries
: Cosmos DB cross-partition queries occur when a query needs to access data from multiple logical partitions, typically because the query lacks a partition key filter or spans multiple partition key values. These queries will increase latency and
resource unit
(
RU
) consumption, leading to slower performance and increased costs.
Evaluate read/write ratio
: This aspect is often overlooked by application and data teams, yet it plays a critical role in performance tuning. By default, Cosmos DB indexes all attributes, which benefits read-heavy workloads but can negatively impact write-heavy ones. In write-intensive scenarios, it is recommended to define a custom indexing policy that limits indexing to only the fields required for queries. This reduces write latency and optimizes resource consumption.
Mind hard limits
: You must always pay attention to hard limits such as the maximum document size, maximum partition size, and so on.
Many of these
considerations can be addressed by choosing an
appropriate partition key strategy. However, some best practices may conflict with one another. For example, selecting a GUID as the partition key can ensure even data distribution and help avoid hot partitions, but it may not align with your query patterns. This misalignment can result in frequent cross-partition queries, which may increase latency and RU consumption.
Back to our wine cellar mobile app scenario, let’s review these considerations against our use case.
We can safely assume the following:
Avoid hot partitions
:
Overall, data should be reasonably evenly distributed, as it is unlikely we’ll encounter extreme imbalances, such as some cellars containing millions of bottles while others have only a few.
Avoid cross-partition queries
: Each user will only access their own collection of wines, meaning that the majority of queries will target a single cellar. While some back-office reporting scenarios may require cross-cellar queries, these are expected to represent a small fraction of the overall query workload.
Evaluate read/write ratio
: Users will most likely generate many more reads than writes as they will be searching for wines, looking at their KPIs, and so on. Writes should be limited to adding/removing bottles from the cellar. We can safely consider this scenario as read-heavy.
Mind hard limits
: A single cellar should not exceed the current hard limit of 20 GB per logical partition. Given typical usage patterns, it is unlikely that a single cellar would contain enough wine documents (wine references) to reach this limit. Likewise, a single wine reference should not exceed the current limit of 2 MB per document, provided we store bottle pictures (if any) outside of Cosmos.
From a functional perspective, we can expect the mobile app to offer a dashboard view as the home screen to help users quickly get aggregates such as the total number of wines in the cellar, average price, quantity per color, and similar metrics.
The app should
also facilitate the
addition of a new bottle by reusing reference data such as wineries, appellations, merchants, and more.

To compute aggregates, we can rely on Azure Functions with a Cosmos DB trigger that uses the
change feed
to capture changes made to wine documents. It’s important to note that the change feed
does not capture delete operations. Therefore, a soft delete strategy—such as marking a wine as deleted with a flag—should be used to ensure
the function gets those deletions and updates aggregates accordingly. We can also optionally leverage the change feed to capture reference data changes and update wines accordingly. Because reference metadata updates are typically not so frequent, this shouldn’t impact the overall performance too much.
For reference data, we use a dedicated container with the
type
attribute as the partition key. This approach allows us to easily distinguish between different document types within the same container. As a result, we will have only three logical partitions—one each for merchants, wineries, and appellations. Given the relatively small size of reference data, we are confident that none of these partitions will approach the 20 GB limit. Furthermore, every query against
RefDataContainer
should include the
type
attribute, ensuring that operations target a single partition for optimal performance and cost efficiency.
For more advanced scenarios, consider using hierarchical partition keys and/or further separating
containers and document types
to better align with access patterns and scalability needs. We hope this example has helped illustrate just how critical thoughtful design is when working with Cosmos DB. Let’s now look at some governance aspects.
Governance
In our governance branch, we can find Databricks Unity Catalog and Microsoft Purview. Both aim to provide

Sensors

high data volumes. Although you haven’t been provided with specific details regarding the number of devices or their data transmission frequency, you can reasonably anticipate a substantial volume of data, making scalability a key design consideration.

Natural language processing
You may not realize it but
Natural Language Processing
(
NLP
) is a very complex field of AI. Natural language is
inherently ambiguous—it includes humor, irony, homonyms, polysemy, and more. Even among humans, miscommunication is common. We often need to
repeat ourselves or clarify our intent by providing additional context.
The most challenging
aspect of NLP is capturing semantics—that is, understanding the meaning of words within their specific context. In traditional AI, we rely on techniques such as
tokenization
. Tokens can represent entire words, subwords, or even individual characters such as punctuation marks. AI models are trained on tokenized text and automatically break down our inputs into tokens during processing. Tokenization is a fundamental technique used by every NLP practitioner. However, tokens alone are not enough to extract semantics. A very popular NLP technique
used to extract semantics is
Part-of-Speech
(
POS
)
tagging
. This technique involves identifying words and their grammatical roles within a sentence, and it remains relevant today. While tokens represent individual, context-free segments of text, tags provide a more comprehensive understanding by revealing the grammatical structure of the sentence.
For example, take the following sentence:
I am Stephane Eyskens, an Azure Cloud Architect.
The corresponding tags would be as follows:
"I" - Pronoun (PRP)
"am" - Verb (VBP)
"Stephane" - Noun (NNP)
"Eyskens" - Noun (NNP)
"," - Punctuation (",")
"an" - Determiner (DT)
"Azure" - Adjective (JJ)
"Cloud" - Noun (NN)
"Architect" - Noun (NN)
. (period) - Punctuation (PUNCT)
Once we have identified each word and its grammatical role in a sentence, we gain a deeper understanding
of the text. Punctuation also plays
a crucial role—symbols such as
.
,
!
, and
?
help indicate sentence boundaries, questions, and emphasis. POS tagging is often performed using stochastic
methods such as
Hidden Markov Models
(
HMMs
), which excel at predicting the most likely sequence of letters, words, tags, or phonemes based on transition probabilities.
However, we still need to refine the phrase further. For example, the word
am
in the preceding sentence is derived from the verb
to be
, like many others, such as
been
,
be
,
is
, and
was
. To identify the parent entity, we rely
on the
lemmatization
technique, which helps reduce noise by identifying the
lemma
of each word. Lemmatization applies not only to verbs but also to nouns, which can have various forms depending on number, gender, and other factors. For instance, the lemma of
mice
is
mouse
. In the preceding example, only the verb
am
differs from its base form. When combined with POS tagging, lemmatization already provides a solid foundation for understanding the core meaning of a text.
Yet, the work doesn’t stop there. As mentioned earlier, language is inherently complex. A given text may include proper nouns, such as names of people, cities, or countries, as well as concepts such as
project management
—all of which are considered
entities
. Identifying these requires the use of
Named Entity Recognition
(
NER
), a technique specifically designed to detect and classify such elements in text.
NER identifies
words or phrases in text that refer to specific, real-world concepts. For example,
Stephane Eyskens
is a person,
Azure
is a cloud platform, and
Cloud Architect
is a job title—each mapped to broader categories such as
Person
,
Cloud Platform
, and
Job
. NER remains a key component of modern NLP pipelines, as recognized entities can be extracted from user input and passed as parameters to downstream systems. For instance, with Azure’s Conversational Language Understanding service, entities are automatically captured from a user query and forwarded to the application code handling the request. This allows developers to define and train models
to extract custom entities, such as a ServiceNow ticket incident number. Even in a GenAI context, entities are captured and passed as
parameters to functions during a function-calling process.

Embeddings generation, vector databases, and hybrid search
We can’t talk
about GenAI without explaining the concept of
embeddings. The rise of deep learning caused
the widespread adoption of the text-embedding concept.
Bidirectional Encoder Representations from Transformers
(
BERT
) is, among others, a transformer-based deep learning model that is able to create embeddings, which are vector-based
numeric representations, where each number is a dimension. The number of dimensions you obtain depends on the model used to generate the embeddings. In Azure OpenAI, there are a few models, such as
text-embedding-ada-002
,
text-embedding-3-large
, and
text-embedding-3-small
.
Other media types, such as images and audio, can be vectorized too, but let’s stick to text for now.
The purpose of text embeddings is to gather as much contextual information as possible and to store it in the form of numeric vectors. Vectors can be compared with others to see whether they look similar or not. Nowadays, we typically compare vectors by calculating their
cosine similarity
, although other comparison techniques exist.
Embeddings support various use cases, including handling vague or ambiguous search queries. Unlike keyword-based search, vector-based search considers the context of the query, enhancing semantic understanding. This allows search engines—or any system processing natural language queries—to retrieve more relevant results from a vector database.
Here is a small example that should help you understand the concept. The following two sentences contain the word
crane
:

As human beings, we instantly identify the context and we understand that, despite
crane
being the same word
in both sentences, it has a totally different meaning because
of the context in which it is used. That is
what transformers such as BERT help identify. BERT would capture the broader context around the word
crane

Retrieval augmentation generation
LLMs are
trained on a huge amount of training data
and parameters. However, they know nothing about your data, unless that data was made public. To compensate for this, the RAG pattern emerged and gained popularity shortly after the rise of GenAI. In essence, it enhances LLMs by incorporating external knowledge—such as your organization’s data—into the generation process. It has been particularly used in
chat with your data
scenarios, although it is not restricted to chatbots.
Figure 8.7
shows two variants of a RAG workflow.
Figure 8.7 – RAG workflow
One way to
achieve RAG for a chatbot is to follow these steps:
The user/system
sends a query to the orchestration API.
The orchestration API retrieves the user query, converts it into a vector (embeddings), and performs a search query against a vector database to find the closest matches (typically using cosine similarity).
Next, the orchestration API forwards both the user query and the retrieved search results to the LLM. The LLM evaluates whether the retrieved information aligns with the query and then generates a coherent, human-readable response.
The alternative approach involves first verifying whether the user’s initial query falls within the chatbot’s scope before proceeding with the vector search. A possible Azure RAG architecture is illustrated in
Figure 8.8

Figure 8.8 – Possible RAG architecture
The frontend
talks to the chat API through
Azure Application Gateway (the WAF) and
Azure API Management
(
APIM

user query to the LLM through API Management, which plays the role of AI gateway. Microsoft has published numerous policies that help deal with AI scenarios, such as load balancing between LLM instances, dealing with token limits, and semantic caching. Additionally, shielding the LLM from the rest of the world is a good practice as APIM can perform some extra token validation —or apply any other policy—while authenticating to the LLM with its managed identity.
AI Search indexers can be used to crawl the prepared data available in a storage account, and we can leverage AI Search’s built-in

One of the benefits of AI Search as a vector database compared to other vector databases is the possibility of leveraging the indexers to fill the vector indexes instead of
having to push vector data ourselves. You may add an extra component to the mix to store the conversation history and the possibility of resuming older conversations.
From a code
perspective, we can use Semantic Kernel, a Microsoft SDK, to deal with the conversation orchestration and to abstract away the AI Search vector database using Semantic Kernel vector stores. This abstraction layer makes it easy to switch to another vector database should the application evolve.
Finally,

As of June 2025, the GPT-4o Realtime API is in public preview and currently supports only speech and audio, not text. Therefore, SSE remains the most effective approach for streaming text responses. Naturally, this choice should be re-evaluated when considering how best to interact with LLMs in the future.
It’s worth noting that the
RAG pattern has several variants, including
GraphRAG

LightRAG

some of the traditional limitations of standard RAG implementations—such as limited contextual understanding and inefficiencies in retrieval and reasoning. Needless to say, regardless of the chosen pattern, the quality of the source data plays a key role in the accuracy of the RAG solution.
Let’s now explore another AI pattern.
Cache augmentation generation
One of the limitations of RAG is its reliance on a vector database with vector or hybrid search capabilities. This retrieval
step can introduce a
performance overhead that may not always be justified. While such a trade-off can be acceptable when working with hundreds of terabytes of data, it becomes less desirable when dealing with smaller knowledge sets, where the cost of retrieval may outweigh the benefits.
The
Cache Augmentation Generation
(
CAG
) pattern is a good alternative as it eliminates the need for a vector database or any other vector memory. It leverages the LLM’s large context window to send the entire knowledge base to the LLM. A context window is the maximum number of tokens LLMs can swallow in one go.
More specifically, we can override the LMM’s KV cache with our knowledge data, once and for all. Any further interaction with the LLM will not require including extra context, and the LLM alone is enough as it has the entire knowledge domain in its cache.

provides a simplified view of CAG.

The first step consists of preparing the knowledge data and uploading it into the LLM’s KV cache. The second and
third steps simply interact with the LLM to query the knowledge domain. Some open source frameworks make this possible, but as of June 2025, there is no
true CAG support in Azure. It is nevertheless interesting to be aware of the pattern as it can be a useful alternative to RAG in some scenarios and could become available in the future.
CAG is particularly
useful for smaller knowledge domains that can fit the context window of an LLM. Beyond RAG and CAG, AI solutions often require extra tooling, which brings us to

Model context protocol
As of June 2025, MCP remains
an emerging pattern
and is highly subject to change in the future, but the philosophy behind it should remain the same.
As noted in the previous section, implementing the TAG pattern at scale can be challenging, since an AI application may need to interface with numerous services, each with its own quirks. This complexity becomes difficult to manage.
MCP partially addresses this challenge by defining a standardized way to describe features and tools. Each tool can implement its own MCP server, while each consuming service maintains its own set of MCP clients. These clients and servers communicate using a common protocol, ensuring consistent interaction patterns.
At this stage, the relationship between each client and server is one to one. The MCP server acts as an abstraction layer over the underlying remote service—such as a database or an API—and encapsulates the logic required to interact with that service.
The application remains the orchestrator between the LLM and its set of MCP resources. However, it no longer needs to implement custom, ad hoc interactions for each individual service and can instead rely on MCP to standardize those interactions.

Figure 8.11 – High-level view of an MCP-enabled application

At this stage of MCP adoption, most AI solutions host both MCP clients and servers themselves. This approach is primarily driven by security concerns, as full trust in MCP—particularly from a security standpoint—has not yet been established.
Typically, service owners develop the MCP server and distribute it as a container image or a package that can be
integrated with different AI solutions.
An MCP server

@server.list_prompts()

@server.get_prompt()

While running a local MCP server is appropriate for accessing local resources, it becomes less suitable for interacting with remote resources exposed by remote services.
The concept of a remote MCP server exists in the MCP specification but is not yet mainstream due to the lack of security. However, in the Azure ecosystem, APIM positions itself as a possible solution for remote MCP servers, as shown in

APIM can also act as a proxy for existing remote MCP servers, helping to standardize how such servers are exposed and consumed across different environments. When integrated with Application Insights, it provides centralized logging and monitoring of all MCP client/server interactions.
While the MCP ecosystem is still evolving, it’s expected that remote MCP servers will become the standard, with local MCP servers being limited to accessing strictly local resources.
Next, let’s explore agentic AI.
Agentic AI
Agentic AI goes beyond being a simple design pattern—it encompasses any autonomous AI system capable of making
decisions and performing tasks without human intervention. For instance, an agent could independently book a hotel room by evaluating factors such as price, comfort, and availability. A key characteristic of agentic AI is the ability of agents to tackle complex tasks, which requires them to reason and formulate a plan to achieve the desired outcome.
An example of a
complex task could be the autonomous planning of a technical intervention of a malfunctioning fridge in a retail store (see the smart fridge monitoring in retail stores use case in
Chapter 7
), detected by a monitoring system. The agent would be triggered by the alert. It should be able to find the most appropriate technician, check availability, and so on. It would take multiple steps and important coordination to make this possible.
However, to achieve this, the agent would most probably leverage a few of the patterns we have learned about so far, such as RAG (knowledge), persist state, TAG (tooling), and MCP (context and tooling), to augment the agent’s capabilities. An agent might rely on other agents to make a decision. This is called multi-agent orchestration. The context, tooling, reasoning, and knowledge can be added using low-code or pro-code solutions.
If you’re just getting started with agentic AI, the Copilot Studio portal is an excellent entry point. It offers a low-code approach that makes it easier to grasp the principles behind agentic AI and achieve meaningful results without the complexity of building everything from scratch.
Copilot Studio integrates seamlessly with the broader Microsoft ecosystem, enabling you to build event-driven agents that can respond to specific triggers—such as receiving an email or the creation of a SharePoint document. You can also schedule agent activities using the
recurrence
trigger type, allowing agents to run at predefined intervals.
For code-based solutions, Semantic Kernel is Microsoft’s open source, enterprise-ready framework designed to orchestrate and manage both single- and multi-agent workflows. In contrast, AutoGen, developed by Microsoft Research, explores more advanced and experimental scenarios but is still evolving and subject to change. For building robust enterprise-grade solutions, Semantic Kernel is the recommended choice.

Magentic orchestration

Next, let’s explore the AI gateway feature of APIM, which can play a key role in whatever AI solution you’re trying to build.
AI gateway through APIM
As discussed earlier, in the
Model context protocol
section, APIM has already embraced the MCP model by positioning
itself as a remote MCP server for APIs published on APIM, or as a proxy to other MCP servers. However, its involvement in the GenAI space goes even further.
The extra
capabilities are part of the API gateway referred to as the AI gateway, but this is the same gateway as for non-AI solutions.
Figure 8.14
shows a subset of capabilities made available by APIM’s AI gateway:
Figure 8.14 – A few AI gateway capabilities
Here is a detailed explanation of each pattern:
Load balancing
: This pattern leverages APIM’s backend pool feature by registering multiple LLMs as backends
of the pool. Additionally, a custom retry policy can be used in case of transient failures of one of the backends or in case of throttling from the LLM. The load-balancing algorithm defaults to round-robin but can be influenced by setting priority and weight-based routing.
Model routing
: At first glance, this pattern might resemble the load-balancing one, but it fulfills a completely
different need. In essence, this pattern consists of routing the request to the appropriate model (different model versions, such as GPT-4o, GPT-3.5, etc.) based on request parameters.
Semantic caching
: This pattern
enables caching of LLM responses in an external store such as Redis, allowing subsequent requests to check the cache for similar prompts before querying the LLM again.
Rate limiting
: This pattern
allows enforcing rate-limiting policies prior to forwarding traffic to the LLMs. This is a good protection against LLMs’ abusive usage.
Message storing
: This pattern
leverages the log-to-eventhub policy to send all messages to Event Hubs. From there on, you can stream those messages with Stream Analytics or other services to get these messages landing in an operational or analytical data store.
Response streaming
: This pattern
ensures that SSE headers are added to the response when needed.
It’s worth
noting that these patterns can be combined, as most are not mutually exclusive.
While additional
patterns exist, this provides a solid foundation to begin with. The key takeaway about the AI gateway is that it shields the client from temporary LLM outages, throttling, and even changes in the underlying model. APIM serves as a bridge between the client and the target LLMs, and it can also handle authentication on their behalf—minimizing direct exposure of the LLMs themselves.
Now, let’s explore a use case.
Use case – AI-driven rule management for tax data processing
Here is
the scenario and first analysis:
Contoso is a well-established company operating in the tax domain. Their core business involves receiving tax transaction files from customers that must undergo validation, cleansing, and compliance checks before being submitted to local tax authorities. The data transformation and compliance rules are highly complex and differ significantly across countries.
Given the high volume of data and the need for low-latency processing, Contoso’s data platform is built on Azure Databricks, which provides the scalability and performance required for large-scale data transformation workloads. The heavy-lifting data transformation process is done by Databricks, but the business performs the final review prior to submitting the resulting files to the authorities.
However, because regulations keep changing, Contoso would like to gain greater agility and aims to empower business users to define these transformation and validation rules using natural language. They currently have a rule engine, but it lacks flexibility and is not intuitive enough. By leveraging AI, the organization seeks to translate these natural language inputs into executable rules that can be integrated back into their underlying data platform.
Before these AI-generated rules are injected into production pipelines, Contoso would like to simulate their application against representative data samples to verify correctness and effectiveness.
Let’s first
extract the keywords in this scenario that demand our focus:
Define data transformation rules using natural language
: Business users would like to define rules by simply expressing them in natural language. This means that we must foresee an NLP-friendly AI model to help us.
Inline validation and injection of the generated rules back into the Azure Databricks data platform
: Databricks performs the heavy-lifting data transformation using broader rulesets that apply to specific countries. We must be able to enrich those rulesets through a feedback loop mechanism.
After some investigation and prompt engineering techniques, we conclude that LLMs are not that good at checking and adjusting data by themselves, especially when dealing with numbers of all types (double, integer, and so on) and calculations. Instead, we realize that we could leverage LLMs to generate PySpark code snippets that implement the rules defined by end users, which we could reinject into Databricks. Effective prompt engineering is essential to ensure that the LLM returns only the relevant code snippet. Once received, the generated code can be displayed to the user, who may choose to execute an in-cluster test against a sample dataset and review the output.
If the user approves the result, the code can be committed to a Git repository—triggering an Azure DevOps pipeline (or an equivalent CI/CD tool) to run a Databricks job on a larger dataset.
This use case demonstrates the value of leveraging code generation rather than relying on the LLM to analyze the data directly. A more effective approach is to express the desired rules and have the LLM generate the corresponding code to implement them.

Summary
This chapter has shown that while GenAI is transforming how we build intelligent applications, traditional AI remains highly relevant for structured, cost-effective, and high-precision tasks. We explored how Azure supports both paradigms through services such as Azure ML, AI Vision, and AI Language, and how foundational NLP techniques such as tokenization, POS tagging, and entity recognition still underpin many modern solutions.
We examined the growing role of embeddings and vector search in GenAI scenarios, comparing Azure’s options and trade-offs for storing and querying vector data. Key architectural patterns, such as RAG, CAG, and TAG, were discussed, each addressing different constraints around data access, performance, and actionability. MCP was introduced as an emerging solution to standardize interactions between AI agents and external tools, helping reduce complexity at scale.
Agentic AI was explored as the natural evolution of these patterns, combining reasoning, planning, and orchestration to tackle complex tasks autonomously. Frameworks such as Semantic Kernel, Dapr, and tools such as Copilot Studio illustrate how both pro-code and low-code solutions can support this shift. Finally, the AI gateway capabilities of APIM were highlighted as essential for building scalable, secure, and resilient AI architectures.
The chapter closed with a practical use case that illustrated how LLMs can generate executable PySpark code from natural language inputs, enabling a feedback loop between business users and data pipelines. Rather than relying on LLMs to interpret data directly, empowering them to generate code offers a more reliable, testable, and maintainable path forward.
