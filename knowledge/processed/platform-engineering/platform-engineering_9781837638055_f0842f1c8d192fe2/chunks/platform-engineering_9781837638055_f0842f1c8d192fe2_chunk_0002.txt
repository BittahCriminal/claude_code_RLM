Implementing continuous Delivery with ArgoCD
Continuous Delivery with Argo CD involves a GitOps approach to manage and deploy applications in Kubernetes. Argo CD is a declarative, GitOps continuous delivery tool that synchronizes applications defined in a Git repository with Kubernetes clusters. It automates deployment by monitoring the specified repository for changes and ensuring that the state in the Kubernetes cluster matches the configurations defined in Git.The prerequisites are the following:
Argo CD installed in your Kubernetes cluster.
kubectl
and
argocd
CLI tools installed and configured to interact with your cluster and Argo CD.
Creating an Application in Argo CD to deploy your application involves a few key steps:
Define the Application in a YAML File
:
Create a YAML file (example,
guestbook-app.yaml
) that defines the Argo CD application. This file should include all necessary configurations, such as the source repository, path, destination cluster, and namespace. Here's an example:
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    path: guestbook
    targetRevision: HEAD
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: false
      selfHeal: false
In this YAML file:
repoURL
is the Git repository URL containing your Kubernetes manifests.
path
is the directory path within the Git repository.
targetRevision
specifies the branch, tag, or commit to synchronize.
server
is the destination Kubernetes cluster.
namespace
is the namespace in the destination cluster where the application will be deployed.
syncPolicy
can be configured for automatic synchronization when a change is pushed in the repository.
Apply the Application Configuration
:
Apply the configuration to create the application in Argo CD:
kubectl apply -f guestbook-app.yaml
This process sets up continuous delivery for your application in Kubernetes using Argo CD. The application's desired state is declared in the Git repository, and Argo CD ensures the Kubernetes cluster's state matches this desired state. This setup enables automated, reliable, and repeatable deployments, adhering to GitOps principles.The ApplicationSet controller is a powerful extension to Argo CD that simplifies managing applications across various Kubernetes clusters or environments. GitOps as your IDP interface
Adopting GitOps as the interface for an IDP presents two primary approaches for organizing repositories: a centralized infrastructure repository or decentralized, team-specific repositories. Both structures have distinct benefits, tailored to different organizational needs.
Centralized infrastructure repository
In this model, all IaC resides in a single repository. This approach fosters a unified strategy for infrastructure management, ensuring consistency and standardization across the organization. There are a number of benefits and challenges in this approach:
Advantages
:
Consistency
: A single source for all infrastructure changes promotes uniform standards and practices.
Easier Oversight
: Centralized control makes it easier for platform teams to oversee and approve changes, ensuring compliance and security.
Shared Knowledge
: Teams can learn from each other's configurations and challenges.
Challenges
:
Potential Bottlenecks
: The approval process can become a bottleneck, slowing down development cycles.
Complexity
: As the organization grows, the repository can become unwieldy and difficult to manage.
Decentralized team-specific repositories
Here, each team manages its own repository containing both application code and IaC. This structure empowers teams to operate independently and enables for scale, other benefits include:
Advantages
:
Speed and Autonomy
: Teams can move quickly, making and deploying changes without waiting for centralized approval.
Focused Context
: Teams only deal with the infrastructure relevant to their services, reducing complexity.
Resilience
: Decentralization can lead to more resilient systems as teams are able to respond and adapt quickly to their specific needs.
Challenges
:
Inconsistency Risk
: Without a centralized standard, there's a risk of divergent practices and configurations.
Overhead of Coordination
: Coordination between teams becomes more critical and potentially challenging.
Duplication of Effort
: Teams might independently solve the same problems, leading to duplicated effort.
Choosing between a centralized or decentralized repository structure for GitOps in an IDP context depends on the organization's size, culture, and specific operational needs, as a result, a third option has emerged.Some organizations might find value in a hybrid approach, where a centralized repository sets global standards and manages core infrastructure (like requesting a new cluster) and decentralized repositories allow teams to innovate and move quickly within those guidelines for other capabilities.Another critical component of our platform is Observability. Collecting metrics with Prometheus and Thanos
Prometheus is a key tool in Kubernetes monitoring that provides a powerful framework for gathering and analyzing metrics. It is particularly well-suited for dynamic, container-based environments like Kubernetes due to its multi-dimensional data model, service discovery capabilities, and modular components. Prometheus is also adaptable, capable of scraping metrics exposed over HTTP and integrating easily with various Kubernetes components.
Installing Prometheus using Helm
To get started, you have to install prometheus in your cluster using Helm. You can use the following command:
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install prometheus prometheus-community/prometheus
To configure Prometheus to scrape metrics from your Kubernetes application, follow these steps:
Edit Prometheus Config
: Modify the
prometheus.yml
configuration file within Prometheus. This file is part of the Prometheus container, typically found at
/etc/prometheus/prometheus.yml
.
Add Scrape Job
: Define a new scrape job within the
scrape_configs
section of the config file:
scrape_configs:
  - job_name: 'kubernetes-application'
    static_configs:
      - targets: ['<application-service-name>:<port>']
Replace
<application-service-name>
with your application's service name in Kubernetes and
<port>
with the port where your application exposes metrics.This configuration directs Prometheus to periodically scrape metrics from the specified application service and port within your Kubernetes cluster.If your application does not have a scraping endpoint for Prometheus, you have a few options:
Instrumentation
: Modify the application code to expose metrics. Prometheus provides client libraries for several programming languages that you can use to instrument your application.
Use an Exporter
: If modifying the application isn't feasible, use an exporter. Exporters are tools that translate metrics from the application's format into the format understood by Prometheus. There are exporters available for various databases, hardware, and third-party services.
Proxy Metrics
: In some cases, you can proxy metrics through another service (like the OpenTelemetry collector show in the following paragraphs) that is capable of exposing the correct format for Prometheus scraping.
Here's a full example, for scraping both Kubernetes deployments and node metrics using the Node Exporter:
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        target_label: __metrics_path__
        regex: (.+)
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_ io_port]
        action: replace
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2
        target_label: __address__
  - job_name: 'node-exporter'
    kubernetes_sd_configs:
      - role: node
    relabel_configs:
      - action: labelmap
        regex: __meta_kubernetes_node_label_(.+)
      - target_label: __address__
        replacement: kubernetes.default.svc:443
      - source_labels: [__meta_kubernetes_node_name]
        regex: (.+)
        target_label: __metrics_path__
        replacement: /api/v1/nodes/$1/proxy/metrics
This configuration sets up Prometheus to scrape metrics from Kubernetes pods and nodes. The
kubernetes-pods
job scrapes metrics from pods annotated for Prometheus scraping, while the
node-exporter
job scrapes metrics from nodes using the Node Exporter. Remember to adjust the configuration to match your specific Kubernetes setup and Prometheus deployment.To enable Prometheus scraping for pods, they should be annotated properly. The necessary annotations are:
prometheus.io/scrape
: Set to
true
to enable scraping for the pod.
prometheus.io/path
: If the metrics path is not the default (
/metrics
), specify the path with this annotation.
prometheus.io/port
: Specify the port on which the metrics are exposed.
For example, a pod's metadata annotations might look like:
annotations:
  prometheus.io/scrape: 'true'
  prometheus.io/path: '/custom_metrics'
  prometheus.io/port: '8080'

Scaling Prometheus with Thanos
Thanos is an open-source project that turns your Prometheus setup into a highly available metric system with long-term storage capabilities. It's designed to operate in a cloud-native environment and can scale horizontally in multi-cluster setups. Thanos addresses some of Prometheus's limitations, especially around long-term storage and high availability as discussed in the following points:
High Availability
: Thanos can be configured to duplicate Prometheus data, ensuring high availability. It does so by connecting to multiple Prometheus instances.
Long-term Storage
: Thanos allows for storing historical metric data for long-term analysis, which is not feasible with a vanilla Prometheus setup. This is particularly useful for capacity planning and compliance.
Query Interface
: Thanos provides a global query view across all connected Prometheus instances, enabling a unified view of data, regardless of cluster location.
Scalable and Efficient
: Thanos is designed to be scalable. It can handle large volumes of data efficiently, making it suitable for large-scale Kubernetes environments.
Cost-Effective Storage
: Thanos integrates with various cloud storage solutions (like S3, GCS, Azure Blob Storage) to store metric data cost-effectively.
To implement Thanos in a multi-cluster environment, you typically deploy components like Thanos Sidecar (next to Prometheus), Thanos Store, Thanos Compactor, and Thanos Query, as shown in the image below.
Figure 7.2 – Thanos Architecture
These components work together to collect, store, and make the data queryable. The Sidecar pushes Prometheus data to a centralized storage backend, the Store provides an interface to this storage, the Compactor optimizes data storage, and the Query component serves as the central query layer across all data.
Centralized logging with Loki
Loki, developed by Grafana Labs, is a logging system designed to store and query logs efficiently. It's especially popular in cloud-native environments for its simplicity and compatibility with Prometheus' service discovery and labeling paradigm. The reason Loki integrates so well with Prometheus:
Loki's Architecture
: Loki's design is inspired by Prometheus. It focuses on simplicity and efficiency, storing logs as streams and indexing only minimal metadata for faster queries.
Promtail for Log Collection
: Promtail, a key component of the Loki stack, is responsible for collecting logs from various sources, primarily Kubernetes pods. It tails log files and sends the data to Loki.
Promtail Pipelines
: They process and enhance the collected logs before sending them to Loki. Pipelines can add, remove, or transform log data and labels.
Integration with Grafana
: Loki integrates seamlessly with Grafana, providing a powerful interface for querying and visualizing log data.
Use in Kubernetes
: Loki and Promtail are particularly effective in Kubernetes, where they can leverage Kubernetes labels and service discovery for efficient log aggregation and querying.

Centralizing M.E.L.T collection with Open Telemetry
The OpenTelemetry Collector serves as a fundamental component for aggregating observability data within Kubernetes clusters. It collects and processes traces, metrics, and logs from various parts of a software system, simplifying the task of gathering and exporting telemetry data in cloud-native environments. This centralized approach to collecting telemetry data is essential for maintaining visibility and operational health of distributed systems.The OpenTelemetry collector has a number of different aspects:
Configuring Data Collection
: The OpenTelemetry Collector's data collection is managed through receivers configured in a YAML file. These receivers act as entry points for data into the collector, responsible for collecting data from various sources.
Processing and Exporting Data
: Once data is collected, it's processed and exported. Processors manipulate, filter, or enhance the data, while exporters define the destination for the data, whether it's an external monitoring system, storage, or another service. This setup allows for customized and efficient handling of telemetry data.
Deployment in Kubernetes
: Deploying the OpenTelemetry Collector in a Kubernetes environment involves creating several manifest files, including ConfigMap, Service Account, Cluster Role, Cluster Role Binding, and Deployment. These Kubernetes resources define how the collector is deployed and managed within the cluster.
Flexible and Scalable
: The collector's flexible configuration and scalability make it ideal for large Kubernetes environments, where it can efficiently collect and manage large volumes of telemetry data from across the cluster.
Vendor-Agnostic
: OpenTelemetry provides a vendor-agnostic approach to telemetry, ensuring that the data collected is standardized and can be used with various back-end systems and visualization tools
The first part of configuring the OTel collector is enabling applications to send data to the collector through receivers:
...

          grpc:
            endpoint: "0.0.0.0:4317"
    processors:

Making data platform capabilities part of your IDP
A modern IDP must enable teams to manage not just applications and infrastructure, but also
data services
in a way that is consistent with the platform's operating model. As organizations adopt microservices and shift responsibility "left", the need to enable self-service provisioning of data services—such as databases, caches, or message queues—has become critical.To operationalize this in a cloud-native context, we'll build a
Database-as-a-Service (DBaaS
) capability within our platform, exposed through a GitOps interface. This will allow developers to provision databases using a GitOps workflow, treating database deployments just like any other Kubernetes resource.In this section, we'll demonstrate how to do this using:
MongoDB Atlas
– a fully-managed cloud database service for MongoDB.
Atlas Kubernetes Operator
– a controller that extends Kubernetes to manage Atlas resources as native Kubernetes objects.
ArgoCD
– a GitOps continuous delivery tool to sync database configurations from a Git repository.The goal is to allow any team to request and manage database infrastructure by submitting YAML files to a version-controlled repository. These YAML files will be picked up by ArgoCD, applied to a Kubernetes cluster where the Atlas Kubernetes Operator is running, and ultimately provisioned and managed in Atlas through its Admin API.
Building the DBaaS capability
Step 1: Set up the MongoDB Atlas Kubernetes Operator
To start, you need a running Kubernetes cluster. The Atlas Kubernetes Operator must be installed in this cluster. You can install the operator using Helm. Once installed, it watches for custom resources such as AtlasProject and AtlasDeployment.Make sure you've generated an Atlas Programmatic API Key with sufficient permissions and added the credentials as Kubernetes secrets in your cluster.
kubectl create secret generic mongodb-atlas-key \
  --from-literal=orgId=<ORG_ID> \
  --from-literal=publicKey=<PUBLIC_KEY> \
  --from-literal=privateKey=<PRIVATE_KEY> \
  -n mongodb-atlas-system
Step 2: Define the AtlasProject Resource
The AtlasProject custom resource is the first resource we need to define. This object creates a new project in MongoDB Atlas and allows us to associate deployments under it. Here's a sample atlas-project.yaml:
apiVersion: atlas.mongodb.com/v1
kind: AtlasProject
metadata:
  name: demo-project
spec:
  name: demo-project
  projectIpAccessList:
    - ipAddress: "0.0.0.0/0"
      comment: "Allow all IPs for demo purposes"
This will provision a new project on MongoDB Atlas and configure an IP whitelist.
Step 3: Define the AtlasDeployment Resource
The next step is to define a deployment that will spin up a MongoDB database within the specified project.
apiVersion: atlas.mongodb.com/v1
kind: AtlasDeployment
metadata:
  name: demo-deployment
spec:
  projectRef:
    name: demo-project
  deploymentSpec:
    name: demo-deployment
    cloudProviderSettings:
      providerName: AWS
      regionName: EU_CENTRAL_1
      instanceSize: M10
      backingProviderName: AWS
    providerBackupEnabled: false
    clusterType: REPLICASET
This will create a single-region replica set named demo-deployment in the
EU_CENTRAL_1
region using the
M10
instance size.
Exposing through a GitOps interface
To enable GitOps-based management, we use ArgoCD to monitor a Git repository and sync the Kubernetes resources stored there into the cluster. We assume ArgoCD is already installed in the cluster.Here's an ArgoCD Application manifest to sync the Atlas project and deployment files from a Git repo:
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: mongodb-dbaas
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/giohan/mongodb-dbaas.git
    targetRevision: HEAD
    path: dbaas
  destination:
    server: https://kubernetes.default.svc
    namespace: mongodb-atlas-system
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
Once applied, ArgoCD will continuously monitor the specified repository in it's specific target revision and ensure that the project and deployment are synced into the destination cluster, triggering the Atlas Kubernetes Operator to provision the actual resources on MongoDB Atlas.

works similarly for Google Cloud resources.
All of these tools enable a consistent GitOps-based experience for infrastructure and data services, reducing the gap between development and operations while increasing autonomy for application teams.

Use Case 1: Observability as code
Observability has become a cornerstone of modern software development and operations. As organizations grow, the complexity of their systems increases, making it crucial to have a unified and standardized approach to observability. This journey often begins with individual teams managing observability in their own ways, evolves into the adoption of standardized practices, and culminates in the implementation of observability as code.In this section, we will explore the stages of this evolution and focus on the transition from each development team implementing observability in non-standard ways, to observability as code, providing practical insights and examples.
Initial Stage: Independent Observability Practices
In the early stages of an organization's growth, different teams often manage observability independently. Each team selects tools and practices that best suit their needs and preferences, leading to a diverse but fragmented observability landscape. While this approach allows teams to tailor their observability solutions to their specific requirements, it also creates several challenges.
First, there is a lack of standardization. Each team may use different metrics, logs, and tracing formats, making it difficult to aggregate and analyze data across the organization. This fragmentation can hinder the ability to gain a holistic view of system performance and health. For example, one team might use Prometheus for monitoring, while another uses Datadog, leading to disparate data sources and dashboards.
Second, managing observability independently can lead to inefficiencies. Each team spends time and resources setting up and maintaining their observability stack, which can result in duplicated efforts and inconsistent quality. Moreover, when incidents occur, the lack of a unified observability approach can slow down the diagnosis and resolution process, as engineers have to navigate through different tools and formats.
To address these issues, the first step is to define the goal of observability and unify the outcomes across the organization. This does not mean imposing a single tool or practice on all teams but rather establishing a common framework for what observability should achieve. A key part of this process is defining
Service Level Objectives
(
SLOs
) that are consistent across the organization.For instance, leadership might decide that all teams should present their SLOs in a standardized manner, focusing on metrics like uptime, response time, and error rates. While each team can still choose their tools and implementation methods, the way they report and interpret these metrics becomes unified. This approach ensures that all teams are aligned in their understanding of system performance and reliability, facilitating better decision-making and cross-team collaboration.
Transition Stage: Templates and Observability as Code
Once the goals and outcomes of observability are unified, the next step is to introduce templates that teams can copy and reuse. This stage marks the beginning of treating observability as code, a practice that brings the principles of
Infrastructure as Code
(
IaC
) to observability.Observability as code involves defining and managing observability configurations through version-controlled code. This practice offers several advantages. It promotes consistency across teams, as templates ensure that all observability setups adhere to the same standards. It also enhances reproducibility and scalability, allowing teams to quickly replicate observability configurations across different environments and projects.To implement observability as code, organizations can use tools like Terraform. Terraform allows teams to define their observability infrastructure using declarative configuration files, which can be stored in version control systems like Git. By using templates, teams can ensure that their observability setups are consistent and aligned with organizational standards.For example, a template for setting up monitoring with Prometheus might include configurations for scraping metrics from various services, setting up alerting rules, and integrating with visualization tools like Grafana. Teams can customize these templates to suit their specific needs while ensuring that the core configurations remain consistent.Here's a simple example of a Terraform template for setting up Prometheus:
provider "kubernetes" {
  config_path = "~/.kube/config"
}
resource "kubernetes_namespace" "monitoring" {
  metadata {
    name = "monitoring"
  }
}
resource "helm_release" "prometheus" {
  name       = "prometheus"
  namespace  = kubernetes_namespace.monitoring.metadata[0].name
  repository = "https://prometheus-community.github.io/helm-charts"
  chart      = "kube-prometheus-stack"
  version    = "14.0.0"
}
This template sets up Prometheus in a Kubernetes cluster using Helm, a package manager for Kubernetes. By providing a standardized template, teams can quickly deploy Prometheus with a consistent configuration across different environments.
Final Stage: Building an Observability Platform
The final stage in the evolution of observability practices is the development of a comprehensive observability platform. As described in
Chapter 6
, this platform integrates various observability tools and practices into a cohesive system that provides a unified view of application performance and health.Building an observability platform involves integrating multiple tools such as Prometheus for monitoring, Thanos for scalable metrics storage, OpenSearch for log management, and Grafana for visualization. This integrated approach ensures that all observability data is collected, stored, and analyzed in a centralized and consistent manner.Here's a high-level overview of the components of an observability platform:
Prometheus
: Collects and stores metrics from applications and infrastructure.
Thanos
: Provides scalable, long-term storage for Prometheus metrics and enables cross-cluster aggregation.
OpenSearch
: Manages logs, allowing for advanced search and analytics capabilities.
Grafana
: Visualizes metrics, logs, and traces, providing dashboards and alerting capabilities.
The platform approach not only standardizes observability practices but also enhances the organization's ability to monitor, diagnose, and resolve issues efficiently. It provides a comprehensive view of system performance and health, enabling teams to detect and respond to incidents faster.Implementing an observability platform requires careful planning and coordination. It involves defining the architecture, selecting the right tools, and integrating them in a way that meets the organization's needs. The platform should be designed to scale with the organization's growth, ensuring that it can handle increasing amounts of observability data.The journey to effective observability involves several stages, from independent practices to standardized templates and ultimately to a comprehensive observability platform. Each stage builds on the previous one, promoting consistency, efficiency, and scalability. Observability as code and setting standards across Metrics, Logs, and Traces, can be one of the first use cases a scaling organization's platform team might tackle.
Implementing Observability as Code with Terraform
Even before building the full capabilities in our IDP we can streamline observability across different environments, using
observability as code (OaC)
, which leverages IaC principles to help us have reusable best practices across diferent teams before we have our platform as product. This approach involves managing monitoring configurations through declarative code using tools like Terraform, integrated with GitOps workflows.Using Terraform for observability, you can ensure consistency, versioning, and transparency in your observability configurations across environments. Every change to observability resources can be reviewed through pull requests, and the changes are automatically applied when merged.In our example, we'll be using Datadog as our monitoring tool, but anyone can work in the same way. To implement Observability as code we'll do the following:
1. Setting Up Terraform for Datadog
First, configure the Datadog provider in Terraform (shown in the code snippet below). This allows Terraform to interact with your Datadog account and manage resources such as monitors and dashboards.//
terraform {
  required_providers {
    datadog = {
      source = "datadog/datadog"
      version = "~> 3.0"
    }
  }
}
provider "datadog" {
  api_key = var.datadog_api_key
  app_key = var.datadog_app_key
}
The datadog provider is used to interact with Datadog's API. The
api_key
and
app_key
variables are stored securely in environment variables or a secrets manager, ensuring sensitive credentials are not hard-coded.
2. Defining Monitors as Code
Next, define monitors to alert on specific conditions within your infrastructure or applications. Datadog monitors track various metrics, logs, and events, sending notifications when predefined conditions are met.
Example
: Creating a monitor for CPU usage that triggers an alert if the average usage exceeds 80% over five minutes:
resource "datadog_monitor" "cpu_usage" {
  name       = "High CPU Usage"
  type       = "metric alert"
  query      = "avg(last_5m):avg:system.cpu.user{*} > 80"
  message    = "CPU usage is too high. Investigate the issue immediately!"
  escalation_message = "Critical CPU usage alert!"
  thresholds {
    critical = 80
    warning  = 70
  }
  notify_no_data    = true
  no_data_timeframe = 10
  notify_audit      = true
}
In the above file, the
datadog_monitor
resource creates an alert for high CPU usage. The query specifies the metric to monitor (
system.cpu.user
) and the condition for triggering an alert (average usage over 5 minutes exceeds 80%). The monitor sends an alert message to your configured communication channels, such as Slack or email, when the threshold is breached. The
notify_no_data
option ensures alerts are triggered if no data is received within the specified timeframe.
3. Creating Dashboards for Monitoring
With Terraform, you can define and automate the creation of dashboards with various widgets, such as timeseries graphs or heatmaps.
Example
: Creating a simple dashboard with a timeseries widget to display CPU usage over time:
resource "datadog_dashboard" "cpu_dashboard" {
  title      = "CPU Usage Dashboard"
  layout_type = "ordered"
  widget {
    timeseries_definition {
      request {
        q   = "avg:system.cpu.user{*}"
        display_type = "line"
        style {
          palette = "cool"
        }
      }
      title = "CPU Usage Over Time"
    }
  }
}
Here the
datadog_dashboard
resource defines a dashboard titled "
CPU Usage Dashboard
." The dashboard contains a timeseries widget that displays the
system.cpu.user
metric with a line graph. You can further customize widgets by adjusting the queries, styles, and other visual properties.
4. Managing Alerts and Dashboards via GitOps
You can start here by having the terraform templates in a centralized repository where anyone can clone, edit, and use for their teams.To integrate observability configurations with GitOps, store your Terraform code in a Git repository. By using Git workflows, such as branching, pull requests, and code reviews, you can collaborate on changes to your observability setup. Every change to the monitoring configurations—whether it's a new alert, updated thresholds, or modified dashboards—goes through a version-controlled pipeline.For example, a team member could propose changes to a monitor by creating a new branch:

Transitioning Legacy Application to Modern Microservices
Transitioning from legacy applications to a modern microservices architecture is a critical process for organizations looking to enhance scalability, maintainability, and agility. This transition, however, is not without its challenges. It requires a deep understanding of existing systems, a strategic approach to decomposition, and the adoption of modern architectural practices. This section delves into the various facets of this transition, starting with an introduction to
Service-Oriented Architecture
(
SOA
) and its relationship to microservices, followed by
Domain-Driven Design
(
DDD
), the Strangler Fig pattern, and the concept of modular monoliths.
SOA
Service-Oriented Architecture
(
SOA
) is an architectural pattern that has been around for decades. It emphasizes the use of discrete services that communicate over a network to perform various functions. SOA aims to promote reuse, integration, and flexibility by encapsulating business logic within services that can be composed to form complex applications.Microservices architecture is an evolution of SOA, taking the principles of service orientation further. While SOA often involves larger, more coarse-grained services, microservices advocate for smaller, fine-grained services that are independently deployable and scalable. Each microservice focuses on a specific business capability and communicates with other services through lightweight protocols, often HTTP/REST or messaging queues.The relationship between SOA and microservices can be understood through their shared goals but differing implementations. SOA laid the groundwork by emphasizing service reuse and integration, which microservices build upon by advocating for autonomy, scalability, and continuous delivery. The transition from SOA to microservices often involves breaking down large, monolithic services into smaller, more manageable microservices that can be developed, deployed, and scaled independently.
DDD
Domain-Driven Design
(
DDD
) is a strategic approach to software development that focuses on modeling software based on the underlying business domain. DDD encourages close collaboration between developers and domain experts to create a shared understanding of the domain and ensure that the software reflects real-world business processes and rules.DDD is particularly relevant to microservices architecture as it provides a methodology for identifying and defining the boundaries of microservices. By using DDD principles, organizations can decompose their monolithic applications into well-defined microservices that align with business capabilities.Key concepts of DDD that facilitate this transition include:
Bounded Contexts
: These are explicit boundaries within which a particular model is defined and applicable. Each bounded context maps closely to a microservice, ensuring that the service encapsulates a specific domain logic and maintains consistency within its boundaries.
Aggregates
: These are clusters of domain objects that can be treated as a single unit. Aggregates ensure that domain invariants are preserved, and they help define the transactional boundaries of microservices.
Entities and Value Objects
: These are the building blocks of the domain model. Entities have a distinct identity and lifecycle, whereas value objects represent descriptive aspects of the domain without identity.
Repositories
: These provide a way to access and persist aggregates. In the context of microservices, repositories often translate to service endpoints that handle data storage and retrieval.
By applying DDD principles, organizations can design microservices that are aligned with business capabilities, promoting clear boundaries, better modularity, and easier maintainability. Using DDD we can also define existing services and use this as the starting point of our migration, using a technique called Strangling the Monolith.
Strangling the Monolith Technique: Breaking Down Microservices from a Monolith
The Strangler Fig pattern is a popular technique for incrementally transforming a monolithic application into a microservices architecture. Inspired by the strangler fig tree that grows around and eventually replaces its host tree, this pattern involves gradually replacing parts of the monolith with microservices until the monolith is fully decomposed, as shown below
Figure 8.4 – The Strangler Pattern – Carving out services gradually out of the monolith
The Strangler Fig pattern involves the following steps:
Identify a Monolithic Component
: Start by identifying a component or functionality within the monolith that can be isolated and re-implemented as a microservice.
Create a Microservice
: Develop a microservice that replicates the functionality of the identified component. Ensure that the new microservice adheres to modern architectural practices, such as being independently deployable and scalable.
Redirect Traffic
: Implement a mechanism to route traffic from the monolith to the new microservice. This can be achieved using a proxy, API gateway, or other routing techniques.
Decommission the Monolith Component
: Once the microservice is fully functional and all traffic is routed to it, decommission the corresponding component within the monolith.
Iterate
: Repeat the process for other components of the monolith, gradually strangling the entire application until it is fully decomposed into microservices.
This incremental approach reduces the risk of disruption and allows for continuous delivery and deployment of new features and improvements. It also provides opportunities to refactor and optimize each component individually, leading to a more modular and maintainable system.While microservices offer significant advantages in terms of scalability and flexibility, they are not always the best solution for every scenario. In some cases, maintaining a modular monolith can provide a balanced approach, combining the simplicity of a monolithic architecture with the modularity of microservices.
The Power of Modular Monoliths
A modular monolith is a monolithic application that is designed with clear modular boundaries. Each module encapsulates a specific business capability and can be developed, tested, and deployed independently, even though they are part of the same deployment unit.The advantages of modular monoliths include:
Simplicity
: Modular monoliths are simpler to develop and deploy compared to microservices, as they avoid the complexities of distributed systems, such as network latency, data consistency, and inter-service communication.
Performance
: Since all modules run within the same process, there are no network overheads associated with inter-module communication, leading to better performance.
Ease of Transition
: For organizations that are not ready to fully commit to microservices, a modular monolith provides a stepping stone. It allows teams to apply microservices principles, such as bounded contexts and modularity, within a monolithic structure.
Unified Deployment
: A modular monolith simplifies deployment and operations, as it is a single service running in our environment, in contrast with running and maintaining multiple microservices.
Transitioning from legacy applications to a modern microservices architecture is a multifaceted process that requires careful planning, strategic execution, and a deep understanding of both the existing systems and modern architectural practices. By leveraging concepts like SOA, DDD, the Strangler Fig pattern, and modular monoliths, organizations can effectively decompose their monoliths and build scalable, maintainable, and agile systems that meet contemporary business needs. This transition not only enhances technical capabilities but also aligns with the broader goals of digital transformation, enabling organizations to innovate and compete in an ever-evolving technological landscape.

Introducing FinOps
Before cloud computing, IT financial management was relatively straightforward. Companies owned and maintained physical servers, storage, and networking equipment, with costs primarily consisting of upfront capital expenditures (CapEx) for hardware and software, followed by operational expenses (OpEx) like maintenance and energy consumption. IT budgets were allocated annually, and finance teams worked closely with IT departments to plan and justify large capital investments. Financial management in this environment focused on maximizing the utilization of these fixed assets and ensuring capacity was sufficient to meet business needs without waste. However, this model had its limitations, including long procurement cycles, difficulty in scaling quickly, and challenges in adapting to changing business requirements.The introduction of cloud computing revolutionized this model, shifting IT financial management from a CapEx-heavy approach to a more flexible OpEx model. Instead of purchasing hardware, companies could now rent computing resources on a pay-as-you-go basis, allowing for greater scalability and responsiveness to changing demands. Cloud production environments are often classified under Cost of Goods Sold (COGS), while development environments fall under OpEx. This distinction requires more refined financial models and cost attribution methods to manage cloud expenses effectively.Nonetheless, the ease of provisioning cloud resources has also introduced challenges, such as
cloud sprawl
– uncontrolled spending on unused or underutilized resources. Traditional financial management practices were insufficient to address this complexity, prompting the development of FinOps, a framework designed to bring financial accountability to the dynamic cloud environment. It focuses on collaboration between finance, engineering, and operations teams to optimize cloud costs and drive business value.
The evolution of FinOps
FinOps began as a response to the need for better cloud cost management. Initially, organizations relied on basic cost monitoring tools from cloud service providers to track their expenditures. As cloud usage grew, third-party tools and platforms emerged, offering more sophisticated capabilities for cost allocation, budgeting, forecasting, and optimization.The establishment of the FinOps Foundation was a milestone in formalizing FinOps as a discipline. The foundation brought together industry leaders, practitioners, and vendors to create standardized practices, frameworks, and training programs, promoting the adoption of FinOps across organizations of all sizes. Today, FinOps encompasses a wide range of activities, from cost tracking and optimization to strategic financial planning, with an emphasis on leveraging data and analytics to drive enhanced decision-making and maximize the value of cloud investments.With its focus on data-driven insights and continuous optimization, FinOps has become essential for organizations looking to maintain control over their cloud expenditures. Understanding why FinOps matters is key to appreciating its growing impact on both financial and operational success.
Why FinOps matters
FinOps is essential for aligning financial and technical goals within an organization. In the cloud era, engineering teams have unprecedented control over resource provisioning, but this can lead to a disconnect between technical decisions and financial outcomes. FinOps bridges this gap by fostering collaboration between finance, engineering, and operations teams, ensuring that technical decisions are made with an understanding of their financial implications.
Enhancing Cost Transparency
One of the core principles of FinOps is cost transparency. In a traditional IT environment, costs were often hidden in large, upfront capital expenditures. In the cloud, costs are dynamic and distributed across various services and teams. FinOps practices provide visibility into these costs, enabling organizations to understand where their money is going and why. This transparency is crucial for identifying areas of waste, optimizing resource usage, and making informed financial decisions.
Driving Financial Accountability
FinOps promotes financial accountability by assigning costs to the teams and individuals responsible for consuming resources. This accountability encourages more responsible behavior and cost-conscious decision-making. When teams are aware of the financial implications of their actions, they are more likely to take steps to optimize their usage and avoid unnecessary expenses. This shift in mindset can lead to significant cost savings and more efficient use of cloud resources.
Optimizing Cloud Spend
One of the primary goals of FinOps is to optimize cloud spend. This involves not only reducing costs but also maximizing the value derived from cloud investments. FinOps practices include continuous monitoring and analysis of cloud usage, identifying opportunities for cost savings, and implementing strategies to achieve those savings. Techniques such as rightsizing instances, leveraging reserved instances, and eliminating unused resources are commonly employed to optimize spend.
Improving Budget Forecasting
Accurate budget forecasting is a critical aspect of financial management, and FinOps plays a key role in improving forecasting accuracy. By providing detailed insights into historical cloud spending patterns and trends, FinOps enables organizations to make more accurate predictions about future costs. This improved forecasting capability helps organizations plan their budgets more effectively, allocate resources more efficiently, and avoid unexpected expenses.As cloud computing continues to transform the way organizations operate, FinOps provides the tools and practices needed to manage cloud costs effectively, align financial and technical goals, and support sustainable business growth. By adopting FinOps, organizations can gain better visibility into their cloud expenditures, drive financial accountability, and optimize their cloud investments for maximum value. To address this need, the FinOps Foundation was created.To further support organizations in adopting and implementing these crucial practices, the FinOps Foundation was established, offering a structured framework and community-driven resources to guide cloud financial management.

The FinOps Cost and Usage Specification, commonly referred to as FOCUS™, is a crucial component of the FinOps Foundation's efforts to standardize cloud financial management practices. FOCUS™ aims to create a common language and framework for describing cloud cost and usage data, enabling organizations to better manage their cloud expenditures and optimize their financial operations. This specification addresses the growing complexity of cloud environments and the need for a unified approach to handling financial data across various cloud service providers.

FOCUS™ was developed in response to the challenges organizations face in managing cloud costs efficiently. As cloud adoption grows, so does the complexity of tracking and analyzing expenses. Each cloud provider uses its own billing structures, terminologies, and reporting formats, making it difficult for organizations to gain a unified view of their cloud spend. FOCUS™ provides a standardized format for cloud cost and usage data, enabling organizations to integrate and analyze this information more easily.The primary goal of FOCUS™ is to improve cost visibility and transparency across the organization. By standardizing how cloud cost and usage data are represented, FOCUS™ allows organizations to compare expenditures across different cloud providers, identify cost-saving opportunities, and make informed financial decisions. It also fosters better communication between finance, engineering, and operations teams, ensuring alignment on cloud spending.To further enhance cost management, FOCUS™ introduces cost attribution strategies that enable organizations to assign specific cloud expenses to individual services, teams, or business units, providing deeper insights into their financial impact
Cost attribution in an Internal Developer Platform
Cost attribution refers to the process of assigning costs to the specific departments, projects, or business units responsible for those expenses. In the context of an
Internal Developer Platform
(
IDP
), cost attribution is crucial for understanding and managing the financial implications of running a platform. It involves breaking down the total expenses incurred from cloud resources, tools, and infrastructure to the various teams and projects utilizing them.The importance of cost attribution cannot be overstated. In a complex, multi-tenant environment like an IDP, where numerous teams and projects share resources, it is essential to have a clear understanding of who is using what and at what cost. This transparency helps organizations manage their budgets more effectively, encourages responsible usage of resources, and aligns financial accountability with resource consumption. By accurately attributing costs, organizations can ensure that each team or project is aware of their spending, promoting a culture of cost consciousness and optimization.Cost attribution also supports better financial planning and forecasting. When costs are precisely attributed, it becomes easier to predict future expenditures based on current usage patterns. This enables more accurate budget allocations and financial planning, helping organizations avoid unexpected costs and allocate resources more efficiently. Furthermore, cost attribution provides the data needed to make informed decisions about investments in infrastructure and services, ensuring that spending aligns with business goals and priorities.Moreover, cost attribution is fundamental for implementing chargeback or showback models, where costs are either billed back to the respective departments or simply reported for transparency. These models drive accountability and can lead to significant cost savings as teams become more aware of their spending and motivated to optimize their usage.However, implementing effective cost attribution comes with challenges:
Tracking complexity
: Cloud services often have variable pricing models (e.g., on-demand, reserved instances, and spot instances), which fluctuate with usage, making accurate cost attribution difficult.
Data granularity
: Accurate cost attribution requires detailed data on resource usage (CPU, memory, storage, network consumption), which can be resource-intensive to collect and analyze. Ensuring the accuracy and completeness of this data is crucial, as any discrepancies can lead to incorrect cost allocations and financial mismanagement.
Shared resources
: Many cloud components, such as networking, security, and storage, are shared by multiple teams. Allocating these costs accurately requires a methodology like proportional usage or predefined ratios. Developing and maintaining these methodologies can be challenging, especially as usage patterns and organizational structures evolve.
Cultural and organizational resistance
: Shifting to a model of financial accountability can face resistance. Implementing cost attribution requires a shift in mindset towards greater financial accountability and transparency, which can be met with resistance if not managed carefully. Clear communication, training, and leadership support are essential for fostering a cost-awareness culture.
Workflow integration
: Organizations often have established processes for budgeting, reporting, and resource management that may not align seamlessly with new cost attribution practices. Integrating cost attribution into existing budgeting and resource management processes can be complex, requiring careful coordination and planning.
To address these challenges, organizations must adopt clear strategies and methodologies for accurate cost distribution across teams and resources, ensuring financial transparency and alignment with business goals.
Methods for Cost Allocation
Cost allocation is a critical aspect of managing cloud expenditures, especially within an
Internal Developer Platform
(
IDP
) where multiple teams and projects share resources. Effective cost allocation ensures that each team or project is charged accurately for the resources they consume, promoting accountability and enabling more precise financial planning. There are several methods for cost allocation, each with its own advantages and challenges. Selecting the right method depends on various factors, including the organization's structure, the nature of the resources being shared, and the specific financial goals.Shared services cost allocation involves distributing the costs of shared resources, such as infrastructure, networking, and security, across multiple teams or projects. This approach is particularly relevant in cloud environments where services are often used by multiple stakeholders. The goal is to allocate these shared costs in a way that reflects the actual usage and benefits derived by each team.There are several strategies for effectively allocating shared services costs. These strategies include:
Direct Allocation
: Costs are allocated directly based on measurable usage metrics. For example, if a shared database service is used by multiple teams, the cost can be allocated based on the number of queries or transactions performed by each team.
Proportional Allocation
: Costs are allocated based on a predefined ratio or proportion. This method is useful when direct measurement is difficult. For instance, if a shared security service protects multiple applications, the cost can be divided based on the relative size or importance of each application.
Fixed Rate Allocation
: Costs are allocated based on a fixed rate or fee. This method simplifies cost allocation by charging a standard fee for each team or project, regardless of actual usage. It is often used for services that provide consistent benefits to all users, such as baseline network security.
Hybrid Allocation
: A combination of different allocation methods is used to best reflect the cost distribution. For example, a shared storage service might allocate costs based on a fixed fee for baseline capacity and a proportional fee for additional usage.
Common Cost Allocation Methods
Accurate cost allocation is key to ensuring financial accountability and optimizing resource usage in cloud environments. Below are some of the most common approaches, ranging from simple to more tailored strategies:
Activity-Based Costing
(
ABC
): Activity-Based Costing (ABC) allocates costs based on the activities that drive those costs. In an IDP, this might involve identifying the various activities involved in providing cloud services, such as computing, storage, and data transfer, and then allocating costs based on the consumption of these activities by different teams or projects. ABC provides a detailed and accurate way to allocate costs but can be complex to implement due to the need for detailed activity tracking.
Resource-Based Costing
: Resource-Based Costing involves allocating costs based on the specific resources consumed by each team or project. This method is straightforward and directly links costs to usage metrics such as CPU hours, gigabytes of storage, or network bandwidth. It is easy to understand and implement but may not account for the indirect costs associated with providing and managing those resources.
User-Based Costing
: User-Based Costing allocates costs based on the number of users or seats assigned to each team or project. This method is often used for software licensing and subscription-based services. It simplifies cost allocation and is easy to administer, but it may not accurately reflect actual usage if the number of users does not correlate with resource consumption.
Time-Based Costing
: Time-Based Costing allocates costs based on the duration that resources are used. For example, costs might be allocated based on the number of hours that virtual machines are running. This method is useful for resources with time-based pricing models but may not capture the full picture of usage efficiency.
Hybrid Costing
: Hybrid Costing combines elements of different allocation methods to create a customized approach that best fits the organization's needs. For example, an organization might use resource-based costing for computing and storage, user-based costing for software licenses, and activity-based costing for support services. Hybrid costing allows for flexibility and can provide a more comprehensive view of costs but may require more effort to manage and maintain.
Selecting the right cost allocation method involves considering several factors to ensure that the chosen approach aligns with the organization's financial goals and operational realities.
Accuracy and Fairness
: The chosen method should provide an accurate and fair distribution of costs. It should reflect the actual usage and benefits derived by each team or project, promoting accountability and encouraging cost-effective behavior. For example, resource-based costing might be appropriate for a cloud environment where usage can be accurately measured and attributed to specific teams.
Simplicity and Transparency
: The cost allocation method should be simple and transparent, making it easy for stakeholders to understand how costs are distributed and why. A complex method might provide more accuracy but can be difficult to administer and explain. User-based costing, for instance, offers simplicity and transparency, making it easier for teams to understand their charges.
Flexibility and Scalability
: The method should be flexible and scalable to accommodate changes in the organization, such as the addition of new teams or projects, changes in resource usage patterns, or shifts in strategic priorities. Hybrid costing, which combines elements of different methods, offers the flexibility needed to adapt to evolving needs.
Cost of Implementation
: The cost of implementing and maintaining the cost allocation method should be considered. Some methods, like activity-based costing, provide high accuracy but can be costly and time-consuming to implement. Simpler methods, like fixed rate allocation, might be less accurate but are easier and cheaper to administer.
Strategic Alignment
: The chosen method should align with the organization's strategic goals. For example, if the goal is to promote efficient resource usage, a method that accurately reflects usage and encourages optimization, such as resource-based costing, might be appropriate. If the goal is to provide predictability and stability in budgeting, a fixed rate allocation might be more suitable.
Stakeholder Buy-In
: Gaining buy-in from stakeholders is crucial for successful implementation. The chosen method should be communicated clearly, and stakeholders should be involved in the decision-making process. Transparent communication and stakeholder engagement help ensure that the method is accepted and adhered to.
By selecting the appropriate cost allocation method, organizations can promote financial accountability, optimize resource usage, and align spending with strategic goals. The choice of method should balance accuracy, simplicity, flexibility, cost, and strategic alignment to meet the organization's specific needs and objectives.With cost allocation serving as a foundation for effective cloud financial management, the next step is implementing practical tools to support these efforts. Cost Management Policies with Kyverno
Integrating OpenCost with Kyverno empowers organizations to implement policy-driven cost governance within Kubernetes clusters. This combination enables automated enforcement of cost allocation rules, ensuring that resource usage aligns with organizational budgets and policies.To monitor and control costs at the namespace level, you can define a ConfigMap that specifies the allocated daily cost for each namespace:
apiVersion: v1
kind: ConfigMap
metadata:
  name: namespace-quota-cm
  namespace: opencost
data:
  argocd: "1"
This ConfigMap assigns a daily cost quota of $1 to the argocd namespace.​By leveraging Kyverno's ability to make external API calls (introduced in version 1.10), it's very easy to integrate Kyverno to pull cost data from OpenCost through a simple API call. Next step, is to implement a Kyverno policy that retrieves actual cost data from OpenCost and compares it against the allocated quota.
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  creationTimestamp: "2025-04-01T00:11:22Z"
  generation: 1
  name: check-namespace-costs-cm
  annotations:
    policies.kyverno.io/title: Namespace Cost Exceeded
    policies.kyverno.io/minversion: 1.10.0
    policies.kyverno.io/category: Cost Management
    policies.kyverno.io/severity: medium
    policies.kyverno.io/subject: Namespace
    policies.kyverno.io/description: >-
      This policy checks for namespace costs and generates a violation if
      the cost exceeds the allocated cost specified in the namespace-
      quota-cm config map.
spec:
  background: true
  rules:
  - context:
    - apiCall:
        method: GET
        service:
          url:
            http://opencost.opencost:9090/model/allocation/
            compute?window=1d&aggregate=namespace&step=1d&accumulate=false
      name: result
    - name: totalCost
      variable:
        value: '{{ result.data[0].["{{ request.object.metadata.name }}"]
        [0].totalCost || ''0'' }}'
    - name: costConfigMap
      configMap:
        name: namespace-quota-cm
        namespace: opencost
    - name: allocatedCost
      variable:
        value: '{{ costConfigMap.data."{{ request.object.metadata.name }}"        || ''0'' }}'
    match:
      any:
      - resources:
          kinds:
          - Namespace
    name: check-namespace-cost
    validate:
      deny:
        conditions:
          all:
          - key: '{{ allocatedCost }}'
            operator: GreaterThan
            value: '0'
          - key: '{{ totalCost }}'
            operator: GreaterThan
            value: '{{ allocatedCost }}'
      message: namespace {{request.object.metadata.name}} cost {{
      totalCost }} exceeds maximum cost threshold {{ allocatedCost }}
  validationFailureAction: Audit
This policy performs the following actions:
Fetches the actual daily cost for each namespace from OpenCost.
Retrieves the allocated cost from the namespace-quota-cm ConfigMap.
Compares the actual cost against the allocated quota.
Generates a policy violation if the actual cost exceeds the allocated quota.
Implementing such policies facilitates proactive cost management, ensuring that Kubernetes resource usage remains within defined financial boundaries
