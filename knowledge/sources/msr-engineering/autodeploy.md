# How it works

The Azure container repo starts either manually, or triggered by a Logic App
## Logic App Configuration
- Create a logic app
- Enable a system assigned or user assigned principal. You can also use an SP if you want another thing to manage
- In the Logic App Designer, use the Recurrence Trigger, and set the interval to what you want
- Add the Azure Resource Manager action, and use Invoke resource operation
- Use the following as an example

```
Subscription: Sesame GCR
Resource Group: autodeployment
Resource Provider: Microsoft.ContainerInstance
Short Resource ID: containerGroups/autodeployment
Client API Version: 2022-09-01
Action Name: start
```
The short resource Id just uses the ACI name with containerGroups before it.
At the bottom it'll ask to make a connector. This will create an "API Connection" azure object when you're done. Use the MSI or User Assigned Identity. Whatever fits best for your use case.

## Azure Container Instance Considerations
Much of the ACI can be deployed using the [Azure bicep configuration](https://dev.azure.com/msresearch/MSR%20Engineering/_git/autodeploy?path=/scripts/ACIdeployscripts/create_autodeploy_container.bicep) and executing with one of the [deployment scripts](https://dev.azure.com/msresearch/MSR%20Engineering/_git/autodeploy?path=/scripts/ACIdeployscripts). You'll need to PIM into the subscription first, since the TnR Devops Role doesn't have permissions to manipulate the Microsoft.ContainerInstance resources yet. 

Deployment is very fast, and much faster than deployment of an IaaS host, or even a new Azure Function deployment. The billing for these containers is roughly equivalent to their IaaS counterparts. However, for the sake of a cron style container, the billing can be very low if it's set to stop when the binary is finished executing. Coupled with a Logic App that has a consumption model, and this resource is very inexpensive to run.

**Note:** 
- If you run the bicep configuration on an active Azure Container Instance, it will clobber the instance with the new configuration.
- You'll need to give the [autodeploymentUAMI](https://ms.portal.azure.com/?feature.msaljs=true&feature.msaljslogin=false&msaljsscript=false#@microsoft.onmicrosoft.com/resource/subscriptions/923239b9-27ca-40bb-9868-3932f1fb42a2/resourceGroups/autodeployment/providers/Microsoft.ManagedIdentity/userAssignedIdentities/autodeploymentUAMI/overview) User Assigned Managed Identity with Contributor access to the ACI for the below Trigger to work. The bicep script doesn't yet do this.

The containers themselves use a [Mariner distroless container](https://eng.ms/docs/products/mariner-linux/gettingstarted/containers/distroless). This means that you can't use the active container to debug, but the attack surface and size of the container is reduced down to ~10MB. This uses the base distroless container as the minimal container would have errors when executing.

If you do spin up a container to debug, ACI has the feature of being able to connect to it via the Azure portal. Logs generated by your script will show up in the portal as well for easy visibility.

Below are the needed variables for the deploy binary. These are the expected values for gpumetrics:

```bash
# The User Assigned Managed Identity ID you are authenticating with.
# This is the Client ID in the User Assigned Managed Identity overview page
USERASSIGNEDIDENTITYID="225fec9a-cba0-4d93-aa61-71e9ea01a050"
# The tag name in AZURETABLENAME below that has the version of the app you wish to deploy
PACKAGEVERSIONTAGNAME="GPUMetricsVersion"
# The Azure Storage account and container where the deploy scripts live
AZURESTORAGEACCOUNT="appautodeployment"
# The Azure Storage Account and Table name where the deploy details live
AZURETABLEACCOUNT="appautodeployment"
AZURETABLENAME="gpumetricsdeploy"
# The Storage Account Key for the AZURESTORAGEACCOUNT above. Used to generate SAS tokens.
# The autodeployment key is here: https://autodeploymentakv.vault.azure.net/secrets/autodeploymentSAKey1/7513a0abae9645fdbf2e4432c2ecce29
AZURESTORAGEKEY=""
```

## Azure Table Setup
The table has the following format:
| PartitionKey | RowKey | ManagementGroup | Query | Script | Key | Value
|-|-|-|-|-|-|-|

With 3 types of rows:
- PartitionKey: **query**
  - These have a Management Group GUID an Azure Resource Graph query in the `Query` column in order to define the scope of what hosts will targeted. You you can have multiple Query rows.
- PartitionKey: **script**
  - This is the code that is run on the host which is a URL in the `Script` column. The script gets passed the AZURESTORAGEKEY as an argument so that the host can download artifacts.
- PartitionKey: **tag**
  - After successfull execution one or more tags can be applied. Their keys and values are defined in the `Key` and `Value` columns.

Running the script will run on all hosts _serially_, not in parallel.

## Permissions
The [autodeploymentUAMI](https://ms.portal.azure.com/?feature.msaljs=true&feature.msaljslogin=false&msaljsscript=false#@microsoft.onmicrosoft.com/resource/subscriptions/923239b9-27ca-40bb-9868-3932f1fb42a2/resourceGroups/autodeployment/providers/Microsoft.ManagedIdentity/userAssignedIdentities/autodeploymentUAMI/overview) User Assigned Managed Identity carries the special permission to query across AMGs and execute the Azure run-command across VMs[¹](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command#limiting-access-to-run-command). Any ACIs need to have this object applied for them to work. This is done automatically with the Azure Bicep script mentioned above.
